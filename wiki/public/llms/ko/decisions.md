# 우리가 내린 엔지니어링 결정

> 대화에서 정한 요구와 변경 이력을 현재 설계·구현·검증·보류 과제에 연결한다

우리가 내린 엔지니어링 결정

이 프로젝트는 Lightning Labs Platform Engineer 지원을 위한 포트폴리오에서 출발했다. 목표는 LND를 한 번 실행하는 데서 끝나지 않고, **다시 배포하고, 상태를 관측하고, 장애를 설명하고, 제한된 대응을 시연할 수 있는 환경**을 만드는 것이다. 이 목표와 실제 장비 제약을 놓고 논의하면서 아래의 선택을 했다.

**아주 쉽게 비유하면:** 놀이 가게를 만들 때 “왜 이 책상을 골랐지?”, “왜 돈통은 치우지 않기로 했지?”를 적어 두는 공책이다. 나중에 가게를 바꾸더라도 원래 이유를 알면 무엇을 유지하고 무엇을 바꿀지 판단할 수 있다. 이런 중요한 설계 선택의 기록을 ADR(Architecture Decision Record)이라고 부른다.

이 기록을 읽는 방법

**논의에서 정한 방향**은 대화와 저장소의 계획 문서에 남아 있는 요구다. **현재 반영**은 코드·runbook·과거 검증 기록을 대조한 내용이다. **대가와 재검토 조건**은 그 선택이 무엇을 해결하지 못하며 언제 바꿔야 하는지 설명한다. 비교를 위한 대안 설명을 대화 당시의 발언이나 별도 승인 이력으로 간주하지 않는다.

대화에서 정한 요구, 코드와 과거 증거에서 확인한 구현, 이번 정리에서 설명한 대안·대가를 구분한다. 운영 클러스터를 새로 검사한 기록은 아니다. 초기 필수 조건 이후 허용한 임시 예외도 함께 표시한다.

ADR-001: 단일 노드 K3s로 플랫폼 운영을 연습한다 {#adr-001}

**논의에서 정한 방향.** Windows 11 Home, 64 GB RAM, 1 TB 장비와 개발용 Mac에서 실제 Lightning Labs 제품을 사용한다. Helm 기반 운영·모니터링·보안까지 포트폴리오에 담기 위해 Kubernetes를 도입한다. 단순 노드 설치를 넘어서 플랫폼을 운영하는 이유를 설명하는 것이 목표다.

**선택 이유.** 단일 LND만 실행한다면 systemd나 Compose도 비교 가능한 방법이다. 이번에는 Kubernetes 리소스, 정책, 장애 대응과 재현성을 다루려 했기 때문에 로컬 K3s를 선택했다. K3s를 사용한다는 사실이 곧 고가용성을 제공한다는 뜻은 아니다.

**현재 반영.** Mac은 Lima의 Linux VM, Windows는 WSL2 Ubuntu에서 각각 K3s를 실행한다. 두 PC가 같은 공유기에 연결돼 있어도 하나의 다중 노드 클러스터를 구성하는 설계는 아니다. 각 환경의 노드와 지갑은 독립적이다. 운영 계획 · Kubernetes 설계

**대가와 재검토 조건.** LND뿐 아니라 Linux VM, K3s API, 네트워크, storage provisioner까지 조사해야 한다. 실제 PVC Pending 장애도 이 비용을 보여 줬다. 단일 장치 장애를 견뎌야 하는 서비스로 전환할 때는 저장소·노드 배치·외부 관측을 새로 설계한다.

ADR-002: 노드 신원과 데이터를 실행 프로세스보다 오래 보존한다 {#adr-002}

**논의에서 정한 방향.** 재배포 때 기존 지갑을 다시 사용할 수 있어야 한다. 따라서 배포가 끝났다는 사실보다 같은 노드를 이어서 운영하는지가 중요하다.

**선택 이유와 현재 반영.** 각 LND를 replicas 1인 StatefulSet과 전용 PVC로 관리한다. regtest의 `lnd-0`, `lnd-1`은 독립된 두 노드이며 같은 지갑의 복제본이 아니다. StatefulSet의 이름과 claim 관계는 재생성 후 같은 데이터를 연결하고 검증하는 데 도움이 된다. Deployment에도 PVC를 연결할 수 있지만, 이번에는 정해진 노드별 관계를 명시적으로 관리하는 쪽을 택했다. LND 템플릿

**대가와 재검토 조건.** StatefulSet은 채널 데이터의 최신성이나 디스크 복제를 대신 보장하지 않는다. local-path 볼륨은 해당 노드의 저장소에 의존한다. 다른 머신에서 같은 신원을 이어받는 failover를 추가하려면 최신 상태의 일관성과 이전 실행자의 확실한 중단부터 설계해야 한다. 상태 보존의 원리

ADR-003: 반복 실험은 regtest, 외부 상호운용은 testnet에서 확인한다 {#adr-003}

**논의에서 정한 방향.** 실제 제품의 노드와 결제 흐름을 보여 주되, 테스트를 반복할 때 외부 자금 공급과 확인 시간만 기다리는 환경은 피하고 싶었다. 실제 진행 중 faucet 제한과 거래 확인 대기도 겪었다.

**선택 이유와 현재 반영.** regtest에서는 Bitcoin Core와 두 LND를 사용해 블록·채널·양방향 지급을 통제한다. testnet에서는 Neutrino 기반 LND로 외부 peer와 실제 네트워크 동작을 확인한다. 네트워크별 values와 namespace, 지갑을 분리한다. testnet의 전체 체인 노드 운영 비용을 줄이는 대신 외부 Neutrino peer에 의존한다. 배포 계약 · 결제 흐름

**대가와 재검토 조건.** 로컬 두 노드 지급 성공은 공개 네트워크의 중계 성공률이 아니다. 외부 peer·경로·서비스가 막히면 해당 검증은 미완료로 남긴다. 같은 funded wallet의 chain backend를 단순 설정 변경처럼 전환하지 않는다. mainnet 적용은 별도의 자금·가용성·복구 검토 대상이다.

ADR-004: 채널 상태에서 송수신·유동성까지 관측 범위를 넓힌다 {#adr-004}

**논의에서 정한 방향과 변화.** 처음에는 노드 운영 지표와 Kubernetes 상태를 정했다. 이후 채널 capacity, L402와 지급 관련 관측을 논의했고, 채널 관측을 중심으로 보다가 송수신과 유동성까지 통합 대시보드에서 보자는 방향으로 확장했다. 그래서 “노드가 켜져 있나” 다음에 “보낼 수 있나, 받을 수 있나, 실제로 완료됐나”가 이어진다.

**선택 이유와 현재 반영.** lndmon으로 기본 LND 지표를 수집하고 부족한 송수신 집계는 별도 collector가 제공한다. Prometheus·Grafana·Alertmanager 설정을 코드로 관리해 재배포 시 같은 질문을 같은 지표로 볼 수 있게 한다. 현재 직접 LND 지급 결과, 방향별 유동성, 지갑·체인·Kubernetes 상태, 백업·보안 신호를 연결한다. 관측 계획 · 신호 해석

**보류 범위.** L402 서비스의 요청·청구·권한 승인 관측은 실제 서비스가 해당 이벤트를 만들 때 추가한다. 직접 LND 결제 데이터를 보여 주는 것을 L402 애플리케이션 통합 완료로 부르지 않는다. 라우팅 중계와 사용자 자신의 송수신도 같은 활동으로 집계하지 않는다.

**대가와 재검토 조건.** 같은 host의 모니터링은 host 전체 중단을 외부에서 발견하지 못한다. 현재 데모 임계값을 실제 사용자 트래픽의 SLO로 그대로 사용하지 않는다. 지급량과 운영 목표가 달라지면 집계 분모·시간 창·실패 분류부터 다시 정한다.

ADR-005: Kubernetes 보안 도구로 필요한 경계를 나누고 별도 방화벽 제품은 넣지 않는다 {#adr-005}

**논의에서 정한 방향.** Kyverno, NetworkPolicy, RBAC 등 기존 Kubernetes 도구를 사용해 중요하고 필요한 통제를 먼저 적용한다. 방화벽을 추가할 수도 있다는 의견은 있었지만, 별도 제품 운영보다 Kubernetes 통신 정책을 우선하는 것으로 정리했다. 실행 중 행위 탐지를 위해 Falco를 포함했다.

**선택 이유와 현재 반영.** 잘못된 배포 조건은 Kyverno, Kubernetes API 권한은 RBAC, Pod 통신은 NetworkPolicy, 실행 중 사건은 Falco가 다룬다. 같은 문제를 네 번 해결하는 것이 아니라 서로 다른 접근 경로와 시점을 검사한다. host firewall은 환경의 별도 전제이며 NetworkPolicy가 이를 대체하지 않는다. 보안 기준 · 심층 방어

**대가와 재검토 조건.** Falco 센서는 높은 host 접근 권한과 커널 호환성 검증을 요구한다. 현재 UID 0 호환성 예외와 sidecar의 넓은 읽기 전용 볼륨 접근도 남아 있다. 도구 설치 수보다 금지 요청 거부와 실제 이벤트 전달 시험이 중요하다. 예외 제거는 이미지·파일 권한·기존 PVC 이전을 함께 검증할 때 진행한다.

ADR-006: Mac Ollama를 재사용하고 모델의 실행 권한은 gateway에서 제한한다 {#adr-006}

**논의에서 정한 방향.** kagent에 LLM을 붙여 runbook 기반 장애 대응을 시연한다. 기존 Mac Ollama를 Windows에서도 호출할 수 있도록 사용하되, model server를 클러스터 안에 반드시 배포할 필요는 없다.

**선택 이유와 현재 반영.** 현재 장비의 모델 실행 능력을 재사용한다. 다만 “Mac endpoint를 사용한다”는 운영 선택을 특정 개인 IP의 소스 코드 고정으로 구현하지 않았다. endpoint는 배포 시 선택하고 개인 상태 디렉터리에 기록한다. 현재 모델 연결이 끊기면 AI 진단이 실패하며 LND 자체의 실행은 별도다. Phase 7 runbook

**자동 대응의 경계.** 모델은 일반 shell이나 kubectl 대신 고정된 MCP 도구를 사용한다. 변경은 진단용 probe 재시작으로 제한한다. cooldown과 허용·거부 감사의 과거 시험 결과는 Windows Phase 7 기록에 남아 있다. 실제 LND 재시작, 지급, unlock, 채널 종료, PVC 삭제, 정책 완화는 모델 도구에 없다. 운영자 승인 API도 아직 없으므로 “승인 필요”는 자동 실행 대기 상태가 아니다.

**대가와 재검토 조건.** LAN과 모델 서버가 추가 의존성이 된다. Phase 7의 peer 정책 원복 주체는 실험 스크립트이며 LLM이 아니다. 현재 시험을 “모델이 자율적으로 LND를 복구했다”로 설명하지 않는다. 자동 조치를 넓히려면 조치별 전제조건, 감사, 중복 방지, 승인, 사후 검증을 먼저 정의한다. 자동 대응 상세

ADR-007: Vault와 cert-manager는 필요한 계약이 생길 때 도입한다 {#adr-007}

**논의에서 정한 방향.** 외장 드라이브가 없는 상황에서 Vault 사용을 검토했고, 보안 확장 단계로 두기로 했다. cert-manager도 Vault 관련 키 관리 등에 필요하면 쓰자는 조건부 후보였다. 따라서 두 제품의 이름이 논의됐다는 이유만으로 설치 완료 항목에 넣지 않는다.

**선택 이유와 현재 반영.** 지금은 운영자가 지갑·복구 입력을 다루며 Vault는 배포돼 있지 않다. LND의 자체 TLS 인증서 만료를 관측하고 수동 회전 절차를 둔다. cert-manager도 현재 별도 issuer·인증서 소비자·회전 계약이 없어 설치하지 않았다. 지갑과 권한 · 보안 기준

**대가와 재검토 조건.** 비밀의 중앙 배포·회전은 아직 수동 운영 영역이다. 여러 운영자나 서비스 자격 증명 수명주기 요구가 생기면 Vault의 초기화·unseal·백업·장애 복구까지 포함해 검토한다. Vault를 같은 PC에 추가하는 것은 별도 장치 백업이나 디스크 암호화의 대체가 아니다.

ADR-008: Mac을 개발용 보조 환경에서 동등한 실행 대상으로 바꾼다 {#adr-008}

**논의에서 정한 변화.** 처음에는 Windows PC에서 실행하고 Mac에서 개발하는 구상이었다. 이후 Mac에서도 동작해야 한다는 요구가 추가됐고, 최종적으로 두 환경에서 같은 수준으로 운영하는 목표로 바뀌었다. 이것은 단순히 Docker 빌드 옵션 하나를 추가하는 요구보다 넓다.

**선택 이유와 현재 반영.** 두 플랫폼에서 같은 Helm chart와 명령 표면을 사용하고 host 준비만 분리한다. 프로젝트 이미지에는 arm64/amd64 지원이 필요하고, 외부 이미지도 고정 digest의 플랫폼 지원을 확인한다. 각 PC는 별도 wallet identity를 사용한다. 같은 네트워크에 있다는 이유로 wallet DB를 복사하거나 같은 신원을 동시에 실행하지 않는다. 배포 계약

**검증 범위.** Phase 8 기록은 양쪽의 독립적 testnet 송수신·관측·보안·상태 보존 재배포를 기록한다. 반면 kagent 실습은 별도의 환경별 전제조건이 있으므로 이 기록으로 모든 AI 데모가 양쪽에서 동일하게 검증됐다고 확대하지 않는다.

**대가와 재검토 조건.** 이미지가 두 아키텍처를 지원해도 커널·스토리지·네트워크 차이는 남는다. 하나의 환경만 통과하면 다른 환경의 검증을 생략하지 않는다. 공통 스크립트를 유지하되 host별 실패를 진단할 수 있어야 한다.

ADR-009: 빈 환경 생성과 기존 지갑 보존 재배포를 별도로 증명한다 {#adr-009}

**논의에서 정한 기준.** “리소스가 아예 없는 환경에서 스크립트를 실행했을 때 정상 동작하는가”를 로드맵의 기준으로 삼았다. 이후 MVP 재배포 시험에서는 이미 만든 지갑을 재사용해도 된다고 완료 조건을 완화했다. 이는 재배포 증명을 위해 기존 지갑을 파기할 필요가 없다는 뜻이다. 빈 환경의 인프라 생성 시험은 별도로 남으며, 그 실행 여부와 결과는 지갑 보존 시험의 성공으로 대신하지 않는다.

**현재 반영.** 첫 시험은 host 전제조건을 갖춘 wallet-free 환경에서 K3s와 프로젝트 리소스를 스크립트로 만든다. 두 번째 시험은 기존 지갑을 유지한 채 chart를 다시 적용하고 node identity, 채널, PVC, SCB, Prometheus 이력을 비교한다. 지갑 생성·seed 보관·자금 공급은 명시적 수동 단계다. 재현성 계약 · clean-start runbook

**대가와 재검토 조건.** “빈 환경”은 WSL 설치 같은 OS 준비까지 아무 권한 없이 자동 처리한다는 뜻이 아니다. 두 종류의 증거를 따로 보관해야 하고, 단계별 스크립트와 기능 검증이 함께 갱신돼야 한다. 일회성 수동 수정에 기대어 성공했다면 재현성 완료로 세지 않는다. 검증 장

ADR-010: SCB는 우선 같은 PC의 K3s 볼륨 밖에 암호화 보관한다 {#adr-010}

**논의에서 정한 방향.** 외장 드라이브가 없고 별도 전송은 운영자가 나중에 수동으로 하기로 했다. 그래서 우선 같은 PC에 백업을 남기는 구조를 택했다. Windows 장치 암호화 기능을 바로 사용할 수 없었을 때는 임시 처리를 허용하고 후속 보안 과제로 남겼다.

**현재 반영.** 각 노드의 SCB를 K3s 데이터 볼륨 밖에 복사하고 파일 암호화와 최신성 확인을 수행한다. seed는 별도로 보관한다. Windows host 암호화 보류는 후속 로드맵에 예외로 기록돼 있다. 초기 계획의 “funding 전 host 암호화 완료”만 읽고 현재 완료했다고 해석하면 안 된다.

**대가와 재검토 조건.** 같은 PC의 원본과 백업은 장치 고장·분실이라는 장애 영역을 공유한다. 파일 암호화도 원본 wallet 전체의 저장장치 암호화와 같은 통제가 아니다. 현재 선택은 완전한 재해 복구 구성이 아니며, 별도 장치 또는 외부 저장소로 확장할 때 전송·복호화·실제 회수 시험을 함께 정한다. SCB와 복구

ADR-011: 관리 화면은 로컬 접속을 기본으로 한다 {#adr-011}

**논의에서 정한 방향.** 관리 인터페이스는 로컬 접속을 사용한다. 집의 같은 공유기에 있다는 사실을 모든 관리 포트 공개의 근거로 삼지 않는다.

**현재 반영.** Grafana와 관리 인터페이스는 로컬 `kubectl port-forward`로 접근한다. Windows 장애를 Mac에서 조사하기 위한 SSH 연결은 운영자의 관리 경로이며, 애플리케이션 공개 endpoint가 아니다. 외부 Ollama 호출은 별도의 필요한 LAN 경로로 취급하고 endpoint·접근 조건을 따로 설정한다. 운영 계획 · agent 접속 경계

**대가와 재검토 조건.** 데모 전에 접속 세션을 준비해야 하고 원격 사용자는 자동으로 접근할 수 없다. 여러 운영자에게 웹 접근을 제공하려면 인증, TLS, 접근 범위, 감사 요구부터 새로 정의한다. 이 결정은 Lightning peer의 네트워크 연결 자체를 로컬에 가둔다는 뜻은 아니다.

ADR-012: 설치뿐 아니라 데모와 세밀한 정리도 스크립트의 계약에 포함한다 {#adr-012}

**논의에서 정한 방향.** 최종 목표를 데모까지로 정했고, 그 뒤에는 삭제 기능도 섬세하게 설계하기로 했다. 기능을 보여 주기 위해 만든 임시 자원과 계속 운영할 지갑·증거를 같은 삭제 대상으로 묶지 않는다.

**현재 반영.** `ops/demo`가 단계별 관측과 regtest 실습을 묶는다. `ops/demo cleanup`은 알려진 프로젝트 소유 임시 자원과 정책 잔여 상태를 다룬다. 증거 정리는 기본 미리보기와 보존 조건을 가지며, 환경 삭제는 대상 profile을 지정하고 지갑 부재를 확인할 수 있을 때만 진행한다. 모호하거나 다른 소유자의 리소스이면 추측해 삭제하지 않는다. 데모·정리 runbook · 정리 구현

**왜 이 정도 검사가 필요한가.** 같은 이름의 리소스가 삭제 계획 이후 새로 만들어질 수 있다. 현재 구현은 삭제 직전에 소유 정보와 UID·resourceVersion을 다시 확인한다. 임시 자원에는 UID·resourceVersion을 검사하는 원자적 JSON Patch로 임의의 정리 표식을 붙이고, 그 표식을 대상으로 삭제한 뒤 기존 UID의 제거와 같은 이름의 대체 자원을 확인한다. 정책 원복도 UID·resourceVersion을 검사하는 patch를 사용한다. 따라서 이름만으로 일괄 삭제하는 절차와 다르다. 이 세부 방식은 “섬세한 삭제” 요구를 코드에서 구현한 방법이며, 대화에서 모든 검사 항목을 하나씩 정했다는 뜻은 아니다.

**대가와 재검토 조건.** 단순 namespace 삭제보다 코드와 검사 경로가 복잡하고, 불확실하면 정리를 거부한다. 강제 종료나 host 장애는 실습의 정상 원복 경로를 건너뛸 수 있어 잔여 상태 점검도 필요하다. 지갑이나 복구 상태를 자동 추측해 정리하는 기능으로 확장하지 않는다.

결정에서 실제 데모까지 읽기

처음 접한다면 LND 사용 흐름을 먼저 읽는다. 그다음 궁금한 결정의 구현 링크를 열고, runbook의 전제조건과 검증 결과를 대조한다. 이 페이지는 실행 명령서가 아니므로 여기서 설명한 삭제·복구·자금 작업을 바로 실행하는 대신 해당 runbook을 따른다.

면접에서는 도구 이름을 나열하기보다 **원래 제약 → 선택 → 받아들인 비용 → 실제로 검증한 범위 → 다음에 바꿀 조건** 순서로 설명할 수 있어야 한다. 예를 들어 “Mac과 Windows에서 실행된다” 다음에는 이미지 지원, host별 기능 검증, 독립 지갑, 아직 별도 검증이 필요한 agent 범위를 함께 말한다.
