# Loop Out 세 번의 실패: 시간을 늘려도 해결되지 않은 문제

> Lightning 노드 운영 회고 6편 · Phase 4 · 2026-09-28 결과 기준

다음 목표는 채널에서 돈이 놓인 방향을 바꾸는 것이었다. 선택한 도구는 Lightning Labs의 Loop였다. Loop Out은 Lightning 쪽 자금을 보내고 온체인으로 받는 방식으로, 채널에 수신 여력을 만드는 데 사용할 수 있다. 반대 방향의 Loop In도 있지만 이번 WSL 실습의 대상은 Loop Out이었다.

개념은 [Lightning Labs의 Loop 설명](https://docs.lightning.engineering/lightning-network-tools/lightning-terminal/loop)을 기준으로 잡았다.

결과부터 말하면 Mac에는 성공 기록이 있었고, WSL에서는 세 번 실패한 뒤 보류했다. 두 호스트는 별도 클러스터·LND 지갑·채널 집합을 사용했으므로, 이 비교로 macOS와 Windows 자체의 성능이나 호환성 차이를 판정한 것은 아니다. 설치 완료를 swap 성공으로 처리하지 않은 것이 이번 단계에서 가장 중요했다.

`swap`은 여기서 Lightning 쪽 자금과 온체인 쪽 자금을 교환하는 작업이다. `Loop Out`은 채널 쪽에서 보내고 온체인 지갑으로 받는다. 돈을 새로 만들어 주는 기능이 아니며 서버·거래 수수료가 들 수 있다.

```text
내 채널의 돈 ── Lightning 경로 ──▶ Loop 서버 쪽
내 온체인 지갑 ◀── 온체인 수령 ── 교환 과정
```

이 그림은 자금의 방향만 보여준다. 실제 교환은 조건부 결제와 온체인 거래를 연결해 처리하므로, 단순히 두 번 독립적으로 송금하는 것과는 다르다.

## 내 쪽 돈을 줄여서 받을 자리를 만들기

내 쪽 잔액이 대부분인 채널은 보내기에는 유리하지만 상대가 나에게 보낼 몫이 부족하다. Loop Out으로 선택한 채널에서 Lightning 결제를 보내면 그 채널의 내 몫이 줄고 상대 몫이 늘어난다. 나는 그 대신 온체인으로 자금을 받는다. 채널을 닫지 않고 채널 안의 자금 배치를 바꾸려던 이유다.

수수료를 제외한 설명용 예로, 내 90,000·상대 10,000인 채널에서 30,000을 보낸다면 내 60,000·상대 40,000 방향으로 바뀐다. 이 숫자는 Loop 서버 최소 금액과 무관한 개념 예시다. 실제 swap은 서버의 금액 제한과 비용, 선택 채널의 제약을 통과해야 한다.

여기서 Mac으로 직접 송금하는 실습과 Loop Out은 다르다. Mac이 일반 Lightning 결제를 받아 주는 것만으로 내 온체인 지갑에 대응 금액을 지급하는 swap 서비스가 되지는 않는다. 이 lab의 Loop daemon은 설정된 외부 testnet swap 서버와 협력한다. 서버와 채널 사이의 경로까지 사용 가능해야 한다.

## Loop는 LND 옆에서 따로 실행된다

Loop는 별도 프로그램으로 실행하고, 접속 권한 파일과 작업 기록을 따로 보관한다. Kubernetes에서 실행 묶음은 Pod, 그 실행을 관리하는 리소스는 여기서 Deployment다. Secret은 접속 권한 파일, PVC는 작업 기록 저장 공간을 연결하는 데 쓴다.

RPC·REST는 프로그램끼리 요청하는 API 방식이고, readiness는 요청을 받을 준비가 됐는지 확인하는 검사다. 아래 그림에서는 “어디에 물어보고 무엇을 저장하는가”를 먼저 보면 된다.

```text
운영 CLI → Loop Pod의 로컬 API
               ├─ TLS + 전용 macaroon → lnd-0:10009
               ├─ 외부 testnet swap 서버:11010
               └─ /loop → loop-data PVC
LND Pod → /data/.lnd → 기존 LND PVC
```

Loop는 LND 안에 내장된 기능을 켜는 방식이 아니라 별도의 `loopd` Deployment로 배치했다. LND PVC를 공유하지 않고, `lnd-loop-credentials` Secret으로 TLS 인증서와 Loop 전용 macaroon을 전달한다. Loop 자신의 작업 기록은 별도 `loop-data` PVC에 남긴다.

Loop API는 Pod 내부 localhost의 RPC 11010·REST 8081로 열고, 외부 Service는 health 수집용 9094만 제공한다. 같은 숫자 11010이 나와도 외부 서버 목적지와 Pod 안의 로컬 API는 주소와 역할이 다르다. readiness는 `loop getinfo`로 확인한다. Pod가 Ready여도 swap 경로와 완료 여부는 다시 확인해야 한다.

실제 `charts/lnd-ops/templates/loop.yaml`의 실행 설정에서 필요한 줄을 추리면 다음과 같다.

```yaml
command: [loopd]
args:
  - --loopdir=/loop
  - --network=testnet
  - --lnd.host=lnd-0:10009
  - --lnd.tlspath=/credentials/tls.cert
  - --lnd.macaroonpath=/credentials/loop.macaroon
```

`loopd`는 계속 실행되는 Loop 프로그램이다. `--loopdir`은 자신의 기록 보관 위치, `--network`는 사용할 네트워크, `--lnd.host`는 요청을 보낼 LND 주소다.

나머지 두 경로는 접속할 LND를 확인하는 인증서와 RPC 작업 권한 파일이다. 실제 template에는 서버 주소·포트·한도도 있다. 이 발췌를 붙여 넣는 것만으로 설치가 끝나는 예시는 아니다.

## 프로그램 연결 완료와 교환 성공은 다르다

계속 실행되는 Loop 프로그램인 daemon에는 LND 접속용 TLS 인증서와 전용 macaroon이 필요했다. macaroon은 여기서 LND RPC 권한을 가진 자격 증명이고, L402는 Loop 서버의 API 접근에 사용되는 결제 기반 인증이다. 서버 API를 사용할 수 있게 된 것, 비용 견적인 quote를 조회한 것, L402 인증을 준비한 것, swap이 성공한 것은 각각 다른 사건이다.

초기에는 `Loop 사용 준비 완료`라는 문구를 보고 Phase 4까지 끝난 것으로 오해하기 쉬웠다. 실제 완료 기준은 양수 금액의 swap 한 건이 `SUCCESS`에 도달하는 것으로 두었다. 서버가 요청을 접수한 `INITIATED`는 성공이 아니다.

LND TLS 인증서는 접속한 서버를 검증하는 데 쓰고, LND용 macaroon은 Loop가 어떤 RPC를 호출할 수 있는지 정한다. 지출하는 swap에 필요한 권한은 단순 조회 권한보다 넓다. 이 lab은 일반 Loop In·Out에 필요한 RPC를 지정해 인증 파일을 만들며, LND 관리자 macaroon을 그대로 복사하는 방식으로 다루지 않는다.

반면 L402는 외부 서비스의 인증·결제 절차다. `fetchl402`에서 `{}`가 나왔다고 “채널 유동성 확보 완료”라고 읽을 수 없다. API 작업의 응답일 뿐 swap 성공 기록이 아니기 때문이다. 실제 실습에서는 L402 준비에 1 sat와 경로 수수료 3 sat가 별도로 지출됐다.

이 때문에 준비 검사와 완료 검사를 나눴다. 저장소 루트에서 `ops/verify-loop --ready`는 서비스와 연결 준비를 확인하고, `ops/verify-loop`는 실제 성공 swap 증거까지 요구한다. 둘 다 검증 명령이며 새 swap을 생성하는 버튼은 아니다.

## 지금 길을 찾는 중인지 블록을 기다리는지 구분하기

| 표시 또는 증거 | 무엇을 의미하나 | 아직 보장하지 않는 것 |
|---|---|---|
| `INITIATED` | swap 요청이 생성됨 | Lightning 결제·온체인 수령 완료 |
| LND `IN_FLIGHT` | 하나 이상의 결제 시도가 아직 진행 중 | 최종 성공·최종 실패 |
| HTLC 관련 온체인 거래 | swap의 온체인 단계가 존재함 | 필요한 확정과 회수 완료 |
| `SUCCESS` | Loop가 최종 성공으로 기록 | 다른 노드·다음 요청의 성공 |
| `FAILED / OFFCHAIN` | Lightning 결제 쪽 실패로 종료 | 모든 관련 금액·비용을 이미 확인함 |

Loop 화면의 상태와 LND payment·HTLC는 서로 다른 수준의 기록이다. `INVOICE_SETTLED` 같은 중간 단계도 이 lab의 완료 기준인 `SUCCESS`와 같지 않다. 블록 확인이 필요한 단계에서는 다음 블록을 기다려야 하지만, 경로 확보 실패를 블록이 느리다는 이유로 설명하면 원인을 놓친다.

설정한 결제 시도 제한이 300초라는 것은 전체 swap을 300초 안에 끝낸다는 약속도 아니다. 이미 전달한 HTLC의 해소와 온체인 확인·회수는 별도 시간을 가질 수 있다. 화면을 닫는 것으로 이 과정이 취소되지 않으므로, 요청을 보낸 후에는 LND와 Loop를 유지하고 최종 상태를 조회해야 한다.

## 첫 실패: 내 돈이 있어도 전달은 끝나지 않았다

WSL에서는 capacity 280,000 sat 채널을 준비했다. 실패 종료 뒤 조회한 내 잔액은 276,526 sat였고, 미해결 HTLC는 없었다. 요청한 Loop Out 금액은 250,000 sat였다.

제출 전 로컬 잔액 검사는 통과했지만, 그것이 전체 경로의 전송 가능성을 보장하지는 않았다. 첫 요청의 Lightning 결제는 여러 조각으로 나뉘었다. 일부 조각은 조건부 결제인 HTLC 상태로 처리되며 `IN_FLIGHT`로 남고 다른 조각에서는 `TEMPORARY_CHANNEL_FAILURE`가 반복됐다.

최종적으로 본 결제가 시간 초과로 끝났고, Loop는 `FAILED / FAILURE_REASON_OFFCHAIN`을 기록했다.

이 요청에서 서버는 선결제용 invoice와 나머지 본 결제용 invoice를 사용했다. 본 결제 231,611 sat와 선결제 30,000 sat는 두 개의 독립적인 swap 원금이 아니다. 두 invoice의 합 261,611 sat는 요청 원금 250,000 sat와 서버 비용 11,611 sat에 해당했다. 실패한 invoice의 금액 표시를 실제 지출로 계산하지도 않았다.

## 바꾼 조건과 결과

| WSL 시도 | 설정 변화 | 본 결제 최종 사유 | Loop 결과 |
|---|---|---|---|
| 1 | 단일 채널, 결제 시도 제한 60초 | `TIMEOUT` | `FAILED / OFFCHAIN` |
| 2 | 단일 채널, 제한 300초 | `NO_ROUTE` | `FAILED / OFFCHAIN` |
| 3 | 공개 채널 3개 허용, 제한 300초 | `NO_ROUTE` | `FAILED / OFFCHAIN` |

첫 수정은 결제 시도 제한을 60초 고정에서 조정 가능하게 만드는 것이었다. 하지만 두 번째 요청은 약 2분 15초에 경로 확보 실패로 끝났다. 설정한 300초를 무조건 채워야 종료되는 것은 아니었다.

다음에는 수동 실행에서 여러 송신 채널을 명시적으로 허용하도록 바꿨다. 기존 UI는 채널 한 개만 선택할 수 있었다. 여러 채널의 합산 잔액을 검사하고 제출 직전에도 각 채널의 상태를 다시 확인하도록 수정했다. 세 번째 요청에서도 16번의 결제 시도 뒤 경로 확보에 실패했다.

이 결과로 단일 채널 제한만이 원인이었다고 말할 수 없게 됐다. 다른 첫 peer에서 시작하는 경로도 계산됐지만 뒤쪽에서는 일부 경로가 겹쳤다. 경로 계산 결과는 실제 송금을 통한 유동성 검증과 다르며, 외부 어느 채널의 잔액이 부족했는지는 확정하지 못했다.

`TEMPORARY_CHANNEL_FAILURE`는 해당 시도의 경로에서 전달에 문제가 생겼다는 단서다. 실패를 보고한 hop 위치는 조사 범위를 좁히지만, 그 공개키만 보고 운영자 장애나 정확한 잔액 부족을 확정할 수는 없다. 시도마다 금액과 경로가 달라질 수 있고, 공개 그래프에서 실시간 잔액을 모두 볼 수도 없기 때문이다.

최종 상태도 우선순위가 있다. payment가 `IN_FLIGHT`인데 `failure_reason`에 `NO_ROUTE`가 보였던 시점에는 남아 있는 HTLC부터 확인했다. 최종 `FAILED`와 빈 inflight 목록이 나온 뒤에는 같은 요청이 그냥 기다리면 성공으로 바뀔 것으로 기대하지 않았다. terminal 결과와 시도 중 단서를 나눠 읽은 것이다.

## 더 작은 금액이라는 우회도 바로 쓸 수 없었다

서버 terms를 조회하니 당시 최소 Loop Out 금액은 250,000 sat였다. 이미 최소 금액을 요청하고 있었으므로 더 작게 나눠 새 swap을 보내는 방식은 사용할 수 없었다. 이 값은 당시 연결한 서버의 응답이지, 모든 서버와 시점의 고정 최소값이 아니다.

세 번 모두 Loop가 기록한 server·onchain·offchain 비용은 0 sat였고, 마지막 조회에서 HTLC가 해소되고 선택 채널 잔액이 돌아온 것을 확인했다. 별도로 앞서 L402 준비에 지출한 1 sat와 라우팅 수수료 3 sat는 남는다. 채널 개설 등 다른 온체인 비용까지 무료였다는 뜻은 아니다.

## 실제로 쓴 돈과 미리 잡아 둔 예산 구분하기

UI의 비용 예약은 온체인에서 돈을 다른 주소로 옮긴다는 뜻이 아니다. 아직 결과를 모르는 요청이 승인된 예산을 중복 사용하지 못하도록 운영 기록에서 잡아 두는 금액이다. 실제 채널 안의 HTLC 잠금과도 다른 개념이다.

현재 구현은 견적에서 서버 비용, 선결제, 채굴 수수료 한도와 각 결제의 라우팅 한도를 확인한다. 현재 Loop Out 비용 예약은 `max(서버 비용, 선결제액) + 채굴 시작 한도 + 본 결제 라우팅 한도 + 선결제 라우팅 한도`로 계산한다. swap 원금 자체를 예약 비용에 더하는 식은 아니며, 채굴 시작 한도는 견적의 두 배로 잡는다. 이는 이 프로젝트의 보수적 예산 검사이고 최종 청구액과 같다는 뜻은 아니다.

요청을 전송하기 전에 고유 label과 제출 의도를 ConfigMap에 기록하고, 응답을 잃으면 같은 label의 swap을 찾아 결과를 대조한다. 응답이 없다는 이유로 자동 재전송하지 않는다.

실패 뒤에도 비용 필드가 없거나 LND 조회가 실패하면 예약을 남긴다. 이번 `OFFCHAIN` 실패는 관련 결제의 종료, HTLC 해소와 비용 필드까지 확인한 뒤 `예산: 실제 비용으로 정산 완료`로 바뀌었다. 이것이 단순히 실패 상태만 보고 0원 처리하는 것과 다른 점이다.

실제 원본을 볼 때는 다음처럼 결과와 비용만 추렸다. 이 명령은 새 swap을 만들지 않는다. kubeconfig 경로는 이 lab에서 이미 준비한 파일을 전제로 한다. 다른 환경에서는 자신의 파일로 바꾸고 Node 목록으로 Mac·WSL 대상을 확인한다.

```bash
export KUBECONFIG="${XDG_STATE_HOME:-$HOME/.local/state}/lnd-ops/kubeconfig"
kubectl config current-context
kubectl get nodes -o wide
kubectl -n lnd-testnet exec deployment/loopd -c loopd -- \
  loop --loopdir=/loop --network=testnet listswaps \
  | jq '.swaps[] | {amt, type, state, failure_reason,
      cost_server, cost_onchain, cost_offchain}'
```

자동 실습도 무한 재시도가 아니다. 현재 lab 구현은 기본 OFF이고 승인한 대상·금액·비용·일일 예산 안에서 화면이 열린 동안 조건을 확인한다. 한 요청이 나가면 추가 요청을 막으며 첫 성공 뒤 멈추고, 실패 시에는 원인을 확인하도록 중지한다. Lightning Terminal의 일반 Autoloop 기능과 이 프로젝트의 제한된 실습 루프를 같은 구현으로 부르지 않았다.

## Mac 성공도 함께 남겨야 했다

같은 날짜의 보존된 Mac 결과 파일에는 250,000 sat Loop Out의 `SUCCESS`가 남아 있다. 비용은 서버 11,614 sat, 온체인 5,550 sat, Lightning 라우팅 6 sat로 총 17,170 sat였다. L402 준비 비용은 별도다.

이는 “Loop가 이 lab에서 한 번도 동작하지 않았다”는 결론을 막는 근거다. 동시에 Mac의 성공이 다른 시점 WSL 경로의 유동성을 보장하지는 않았다. 호스트별로 성공과 실패를 그대로 기록하는 편이 정확했다.

## 실패는 실패로 남기고 다음 실습으로 넘어가기

결국 WSL Phase 4는 미완료로 보류하고 관측 환경 실습으로 넘어갔다. 실패한 swap은 코드 수정 후에도 실패 기록으로 남긴다. 재실행한 프로그램이 과거 결과를 성공으로 바꾸어 보여주면 안 된다.

남은 과제는 경로에 대한 추가 근거를 확보하는 일이다. 이번 실습에서 얻은 것은 확정된 외부 장애 원인이 아니라, 설치·인증·로컬 잔액과 실제 경로 성공을 분리해 확인하는 방법이었다.

관련 구현: [Loop runbook](../phase2-loop-runbook.md), [요청·예산 검사](../../ops/loop_ops.py). Mac 수치는 비공개 원본에서 허용된 결과·비용 필드만 재확인했고, 원본 파일은 게시하지 않는다.
