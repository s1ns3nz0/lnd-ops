# 채널은 연결이 아니었다: 잔액과 유동성 이해하기

> Lightning 노드 운영 회고 4편 · Phase 3 전반 · 2026-09-27~28 실습 출력 기준

상대에게 전화가 연결됐다고 그 사람에게 보낼 돈까지 준비된 것은 아니다. Lightning도 연결과 돈을 보내는 준비가 다르다. `active: true`를 봤을 때도 “얼마를 어느 방향으로 보낼 수 있지?”를 따로 물어봐야 했다.

이 실습은 Mac과 WSL의 별도 Kubernetes 클러스터에 testnet LND를 띄우고, 프로젝트의 터미널 도구 `lndops`로 진행했다. 아래에서 말하는 UI는 LND 공식 GUI가 아니라 이 도구의 채널·진행 화면이다.

sat는 Bitcoin 금액 단위이며 1 BTC는 100,000,000 sat다. 아래 숫자는 모두 시험용 네트워크에서 다룬 금액이다.

채널을 두 사람이 나눠 쓰는 돈주머니로 생각해 보자. 주머니 전체 크기가 `capacity`이고, 그 안에서 내 몫은 `local_balance`, 상대 몫은 `remote_balance`다.

내가 상대에게 결제하면 내 몫이 줄고 상대 몫이 늘어난다. 실제로는 서명된 채널 상태를 갱신하는 방식이며, 매번 Bitcoin 블록에 새 송금을 기록하는 것은 아니다. 비유에서 기억할 것은 **전체 크기와 내 몫이 다르다**는 점이다.

## 상대와 연결하기와 채널 열기는 다르다

peer 연결은 두 노드가 통신할 수 있는 관계다. 채널은 그 관계 위에 자금을 배치하고 결제 상태를 갱신할 수 있게 하는 별도 구조다. 따라서 peer 수와 채널 수가 일치할 필요는 없다. 같은 상대와 채널을 여러 개 열 수도 있다.

온체인 지갑에는 아직 채널에 배치하지 않은 Bitcoin 잔액이 있다. 채널을 열면 채널을 여는 온체인 거래인 funding transaction으로 자금이 잠기고, 채널 안에서 어느 쪽이 얼마를 받을 권리를 갖는지 갱신한다.

Lightning의 채널과 조건부 결제 구조는 [BOLT 소개 문서](https://github.com/lightning/bolts/blob/master/00-introduction.md)를 기준으로 이해했다.

## 돈이 지갑에 있는지 채널에 있는지 나누어 보기

온체인 지갑 잔액은 지갑이 관리하는 Bitcoin 출력 중 잔액으로 잡힌 금액이다. 채널의 funding 출력에 배치한 금액은 채널 안의 잔액으로 따로 봐야 한다. 같은 돈을 “원래 지갑에 있던 돈”과 “채널 capacity”에 각각 더하면 자산을 중복 계산하게 된다.

| 조회 항목 | 이 실습에서 읽는 의미 | 흔한 오해 |
|---|---|---|
| `confirmed_balance` | 확정된 온체인 지갑 잔액 | 전부 새 채널에 쓸 수 있다고 판단 |
| `unconfirmed_balance` | 아직 확정되지 않은 지갑 잔액 | 입금 표시만 보고 바로 확정 자금으로 취급 |
| `capacity` | 그 채널 전체 용량 | 전부 내 소유로 계산 |
| `local_balance` | 현재 노드 쪽에 배분된 채널 잔액 | 표시 금액 전부가 즉시 송신 가능하다고 판단 |
| `remote_balance` | 상대 쪽에 배분된 채널 잔액 | 내 전체 자산에 더함 |

Mac과 WSL을 함께 운영하더라도 채널 한 개를 양쪽에서 조회하면 관점이 뒤집힌다. WSL의 local은 Mac에서 remote로 보이는 방향이다. 같은 채널을 두 개의 독립 자산처럼 합산하지 않으려면 상대 공개키뿐 아니라 funding 거래와 출력 번호인 `channel_point`로 연결 관계를 확인해야 한다.

전체 잔액 스냅샷을 만들 때는 노드 identity, 조회 시각, 온체인 잔액, 채널별 잔액, pending 상태를 함께 기록한다. 이번 글에 나오는 여러 숫자는 다른 시점의 실습 출력이므로 하나의 현재 자산 명세로 합치지 않았다.

## local은 내 쪽, remote는 상대 쪽이다

아래 조회의 `lnc`는 현재 터미널에서 선택한 testnet LND를 호출하는 함수다. 독립적으로 따라 읽을 수 있도록 정의도 함께 둔다. Mac과 WSL에서는 각각 자신의 kubeconfig와 노드 identity를 먼저 확인한다.

```bash
export KUBECONFIG="${XDG_STATE_HOME:-$HOME/.local/state}/lnd-ops/kubeconfig"
lnc() {
  kubectl --kubeconfig="$KUBECONFIG" -n lnd-testnet exec lnd-0-0 -c lnd -- \
    lncli --lnddir=/data/.lnd --network=testnet "$@"
}
lnc getinfo | jq '{identity_pubkey, alias}'
```

채널 조회에서 필요한 항목만 추렸다.

```bash
lnc listchannels | jq '.channels[] | {
  remote_pubkey, active, capacity, local_balance, remote_balance
}'
```

위 코드에서 `.channels[]`는 “채널을 하나씩 꺼내라”는 뜻이다. 중괄호 안의 다섯 필드는 “그 채널에서 이 정보만 보여줘”라는 뜻이다. 채널을 만들거나 잔액을 바꾸는 명령은 아니다.

실습 당시 WSL의 채널 중에는 다음처럼 보이는 채널이 있었다.

```json
{
  "active": true,
  "capacity": "100000",
  "local_balance": "96530",
  "remote_balance": "0"
}
```

이 채널을 보고 처음에는 잔액이 0이니 사용할 수 없는 것 아닌가 생각했다. 하지만 0은 상대 쪽 잔액이었다. 내 쪽 자금으로 보내는 데 쓸 여지는 있지만, 상대가 이 채널을 통해 나에게 보낼 여력은 없는 상태로 이해해야 했다. 표시된 잔액을 전부 보낼 수 있는 것은 아니다.

채널 안에 남겨야 하는 최소 잔액인 reserve, 종료에 사용할 거래의 비용인 commitment fee, 아직 처리 중인 조건부 결제인 HTLC와 채널 정책도 영향을 준다.

따라서 `active`는 연결·채널 상태를 보는 신호이고, 원하는 금액을 양방향으로 주고받을 수 있다는 보증은 아니었다. `capacity`와 양쪽 표시 잔액의 합이 다른 것도 표시 오류라고 단정할 수 없었다.

수수료와 reserve를 잠시 제외한 설명용 예로, 100,000 sat 채널이 내 70,000·상대 30,000으로 나뉘었다고 하자. 내가 상대에게 10,000 sat를 보내면 내 몫은 60,000, 상대 몫은 40,000이 된다. 채널 전체 용량은 그대로이고 분배만 바뀐다. 상대에게 보낼 여력은 줄고, 상대가 나에게 되돌려 보낼 여력은 늘어난다.

중계 노드는 이 변화가 두 채널에서 동시에 일어난다. 들어오는 채널에서는 내 몫이 늘고, 나가는 채널에서는 내 몫이 줄어든다. 따라서 모든 채널에 내 잔액만 가득 채우는 방식은 수신 방향을 준비하는 방법이 아니다.

앞의 실제 예에서는 `100000 - 96530 - 0 = 3470 sat`가 표시 잔액 합계에서 빠져 있다. 이 차이만으로 사라진 돈이라고 판단하지 않는다. commitment transaction 수수료와 처리 중인 HTLC 등 해당 채널의 회계 필드를 함께 봐야 한다. channel reserve는 잔액 중 사용할 수 없는 하한으로 작용하므로, 차액 전부를 reserve라고 부르는 것도 부정확하다.

```bash
lnc listchannels | jq '.channels[] | {
  channel_point, capacity, local_balance, remote_balance, commit_fee,
  local_constraints, remote_constraints, pending_htlcs
}'
```

핵심은 capacity에서 뺄셈 한 번으로 실제 송신 가능액을 확정하지 않는 것이다. 이 lab의 UI도 별도 보수적 검사를 하지만, 그 검사를 통과한 금액이 외부 전체 경로를 통과한다는 보장은 아니다.

## 남겨 둘 돈이 있어서 전액을 넣지 못했다

채널을 추가할 때 다음 오류를 만났다.

```text
reserved wallet balance invalidated:
transaction would leave insufficient funds for fee bumping anchor channel closings
```

노드가 anchor 채널의 종료 수수료 보강을 위해 남겨두려는 온체인 자금까지 사용하려 했다는 오류였다. faucet에서 받은 잔액이 보인다고 그 전액을 새 채널에 넣을 수 있는 것은 아니었다.

당시 WSL 지갑 조회에는 확정 잔액 377,778 sat와 anchor 예약금 20,000 sat가 함께 나왔다. 단순 차액은 357,778 sat지만 그것을 그대로 개설 가능 금액으로 단정하지 않았다. funding transaction 수수료와 추가 예약 조건도 고려해야 했다. anchor 예약금은 이미 지출된 수수료와도 구분했다.

온체인 anchor 예약과 채널 reserve도 위치가 다르다. 앞의 오류에서 말하는 anchor 예약금은 채널 종료 상황에서 수수료를 보강하는 데 사용할 온체인 여유 자금이다. 채널 reserve는 채널 내부에서 상대와 합의한 잔액 제약이다. 둘 다 “남겨둬야 할 돈”처럼 보여도 같은 필드가 아니다.

## 채널을 열 때 정했던 값의 의미

| 입력값 | 무엇을 정하나 | 실습에서 주의한 점 |
|---|---|---|
| 상대 노드 공개키·주소 | 누구와 통신하고 채널을 만들 것인가 | IP만으로 노드 identity를 대신하지 않음 |
| `local_amt` | 내 온체인 자금으로 넣을 채널 금액 | funding 수수료와 온체인 예약금 별도 |
| `push_amt` | 개설 시 상대에게 배분할 금액 | 상대 몫으로 넘기는 금액이며 내 예치금이 아님 |
| 공개·비공개 여부 | 채널을 공개 그래프에 알릴지 | 비공개가 암호화 여부를 뜻하지 않음 |
| `sat_per_vbyte` | funding 거래 수수료율 | 총 수수료 금액과 구분 |
| `min_confs` | 사용할 지갑 입력의 최소 확인 수 | 채널 활성화에 필요한 funding 확인 수와 구분 |

특히 `push_amt`는 수신 여력을 만들 수 있지만 상대에게 자금을 넘기는 선택이다. 이전 runbook의 특정 push 예시는 testnet 실습을 위한 조건이었다. 운영자가 바뀌었는데 같은 숫자를 무심코 복사하는 설정으로 다루지 않았다.

수수료율도 크기 단위를 알아야 읽힌다. 설명용으로 201 vB 거래에 50 sat/vB를 적용하면 예상 수수료는 10,050 sat다. 50 sat를 한 번 내는 것이 아니다. 실제 거래 크기와 최종 수수료는 입력·출력 구성에 따라 확인해야 한다.

## 채널이 활성화되기까지 기다리는 이유

WSL에서 새로 연 280,000 sat 채널은 처음에 `confirmations_until_active: 3`으로 나왔다. 이후 1로 줄고 pending 목록에서 사라졌다. 목록에서 사라진 것만으로 성공을 단정하지 않고, `listchannels`에서 해당 채널의 활성 상태를 확인하는 흐름이 필요했다.

또 CLI 화면을 종료하는 것과 채널을 닫는 것도 달랐다. `q`나 터미널 종료는 조회 프로그램을 끝낼 뿐이다. LND와 채널 상태는 계속 남아 있었다.

채널 활성화 뒤에는 중계 수수료 정책도 따로 설정했다. 이 lab의 목표 기본값은 base fee 1,000 msat와 비례 수수료 500 ppm이다. 1,000 msat는 1 sat이고, 500 ppm은 전달 금액의 0.05%다. 이는 funding 거래를 채굴하기 위해 지불한 수수료와 다른 항목이다. 정책이 목표와 일치하는지, 시험 금액이 HTLC 최소·최대 범위에 들어가는지까지 봐야 lab의 준비 조건을 충족한다.

## 연결 종료·화면 종료·채널 종료는 다르다

peer 연결이 끊기면 채널이 비활성으로 보일 수 있지만 그것만으로 funding 자금이 온체인 지갑에 돌아오지는 않는다. 화면을 종료하는 `q`는 조회를 끝낸다. 채널을 닫으려면 별도의 close 절차와 온체인 정산을 거친다.

이 lab의 종료 UI는 활성 상대와 일반 종료를 요청하는 기능이며 강제 종료를 자동 대안으로 제공하지 않는다. 종료 요청을 보냈다는 응답 뒤에도 pending 상태와 종료 거래 확정, 실제 지갑 잔액을 확인해야 한다. 종료 수수료가 있고, 강제 종료라면 기다려야 하는 출력도 생길 수 있어 capacity 전액이 즉시 반환된다는 식으로 설명할 수 없다.

이 단계에서부터는 “잔액이 얼마인가” 대신 “어떤 지갑에 있고, 어떤 채널의 어느 방향으로 사용할 수 있는가”를 묻게 됐다. 이 질문이 다음 중계 실습과 Loop Out 실패 분석의 출발점이었다.
