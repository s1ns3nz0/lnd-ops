# Mac stage 4 monitoring infrastructure reset evidence (2026-09-22)

This proves the monitoring infrastructure slice on Mac arm64. It does not prove the stage 4 LND signal, dashboard, alert, or Windows exit checks.

1. Installed the vendored kube-prometheus-stack 91.4.1 chart with pinned image digests using `ops/deploy-monitoring`. Grafana health reported its database `ok`; Prometheus queried 13 live `up` targets, including node exporter and kube-state-metrics. Host filesystem and Kubernetes Pod series were present. The Prometheus custom resource specified 14-day retention, and Alertmanager had an available replica.
2. Repeated `ops/deploy-monitoring` against the existing release. The Prometheus PVC UID stayed `99643435-5213-4c52-ad58-b1e8566f0911`, and the earliest Prometheus sample timestamp stayed `1790065254046`, demonstrating ordinary upgrade preserved the monitoring volume and history.
3. Deleted the disposable `lnd-monitoring` namespace with `kubectl delete namespace lnd-monitoring --wait=true`. Reran `ops/deploy-monitoring` and `ops/verify-monitoring --infrastructure-only`. The namespace, release, Pods, and 10 GiB Bound PVC were recreated. Grafana, Prometheus, Alertmanager, node exporter, Kubernetes Pod, and disk checks passed. The new PVC UID was `3e93e11a-7eef-4fb6-958b-dd0ee6738009`.
4. Reran `ops/deploy-monitoring` after adding an explicit post-Helm readiness check. Revision 2 completed and the same infrastructure verifier passed. The reset PVC UID was preserved.
5. Provisioned `LND Ops / Kubernetes` from `charts/dashboards/kubernetes.json`, then ran `ops/deploy-monitoring` again. Grafana's authenticated dashboard API returned UID `lnd-ops-kubernetes`, title `LND Ops / Kubernetes`, and four panels. All four panel PromQL expressions returned successful Prometheus queries with nonempty result sets on Mac; node readiness, LND Pod readiness, guest filesystem free space, and monitoring scrape targets were present.
6. Deleted the monitoring namespace again, then ran `ops/deploy-monitoring` from its absence. Revision 1 recreated all Pods and a new Bound PVC (`963ac562-05f4-4218-a2ad-44f2a9382bfe`). `ops/verify-monitoring --infrastructure-only` passed as part of the deploy command. Grafana's authenticated API returned the same project dashboard UID and four panels after this reset.
7. Added `LndOpsPodNotReady` and `LndOpsGuestDiskLow` PrometheusRules. Prometheus `/api/v1/rules` reported both loaded and healthy. Applied the disposable `tests/fixtures/pod-not-ready.yaml`, which forbids image pulls and deliberately leaves the Pod unready. The `kube_pod_status_ready{condition="false"}` sample became `1`, Prometheus moved `LndOpsPodNotReady` through pending, and Alertmanager `/api/v2/alerts` returned the matching Pod alert as `active`. Deleted the test Pod afterward.
8. Deleted `lnd-monitoring` again and ran `ops/deploy-monitoring` from namespace absence. It recreated all six Ready monitoring Pods and a new Bound Prometheus PVC (`52ff8f88-63e1-481d-bab3-11901fc6a15b`). The deploy command's infrastructure verifier confirmed the two alert rules were loaded. Grafana's authenticated API again returned `lnd-ops-kubernetes` with four panels. This reset did not erase the separate `lnd-regtest` namespace.

Grafana's authenticated API returned all four project dashboard UIDs with 4, 7, 8, and 6 panels respectively. Prometheus parsed all 21 new panel PromQL expressions successfully. No LND time series existed yet, so those panels have not passed live-data checks.
10. Deleted `lnd-monitoring` again and ran `ops/deploy-monitoring` from namespace absence. Six monitoring Pods became Ready, the Prometheus PVC was recreated (`f629199d-a2a7-4438-abe4-47fc08f8ee21`), and the infrastructure verifier passed. Grafana's authenticated API again returned all four dashboard UIDs with the same panel counts. The regtest and testnet LND namespaces remained untouched.
11. Added the explicit `ops/deploy testnet --monitoring` gate. On the empty testnet wallet, it exited `10` before Helm mutation, and the testnet release stayed at revision 1. A subsequent ordinary `ops/deploy testnet` upgraded to revision 2 with the same LND Pod age and PVC UID (`65e1069a-6fdc-4c02-a6f1-0fd677698960`). 15. Ran the arm64 payment collector image against a disposable HTTPS LND fixture. 16. Added chain-sync-stalled, inactive-channel, lndmon-unavailable, and payment-collector-unavailable rules with runbooks. Deleted `lnd-monitoring`, confirmed absence, then reran `ops/deploy-monitoring`; the new release was revision 1 with six Running Pods and a new Bound PVC `b14987a6-a444-461e-b4e4-d2c29c87240d`. Prometheus reported all six project alert rules loaded with health `ok`. Their LND-specific firing paths remain untested until an unlocked wallet supplies metrics.
17. Ran `ops/test-lnd-alerts` on Mac arm64. It built and loaded the pinned collector image for a disposable metrics Pod, then exposed `lnd_chain_synced 0` and `lnd_channels_inactive_total 1` through a regtest Service. Prometheus discovered the fixture as a healthy `lndmon` target. Both `LndOpsChainSyncStalled` and `LndOpsChannelInactive` entered pending, passed the five-minute rule duration, and were reported active by Alertmanager; the runner exited `0`. Its cleanup removed the fixture Pod, Service, and NetworkPolicy, confirmed by a subsequent resource listing. The first attempt was interrupted after a separate manual API probe used the wrong kubeconfig; a later probe with the project kubeconfig showed that both Service proxy URL forms work. This is a synthetic alert-delivery test, not proof that live LND emits the expected metrics or that a real node fault reaches the rules.
18. Called the pinned regtest LND Pod's TLS `/v1/state` endpoint through a local port forward without a macaroon; it returned `NON_EXISTING` before wallet creation. Added a fixed one-hot wallet-state metric to the collector and confirmed its read function converted that live response. Five Python collector tests passed. Built and imported the changed arm64 image `localhost/lnd-ops-payment-collector:8221630d886cdeac`; Buildx built the same source for amd64 and the amd64 container loaded the new function. Upgraded monitoring twice to revision 3 while keeping Prometheus PVC UID `b14987a6-a444-461e-b4e4-d2c29c87240d`. `ops/verify-monitoring --infrastructure-only` passed with eight healthy project rules and the new wallet-state scrape job. Grafana's API returned the Overview dashboard with eight panels, including the wallet/RPC state panel.
19. Ran `ops/test-lnd-alerts --wallet-locked`. The disposable fixture exposed a `LOCKED` state and, at the same time, chain-not-synced and inactive-channel metrics with a healthy lndmon scrape. Prometheus moved only `LndOpsWalletLocked` to pending; after two minutes Alertmanager reported it active. The runner confirmed dependent chain, channel, lndmon-unavailable, and payment-collector-unavailable alerts were absent for that Service, then exited `0`. It removed its Pod, Service, and NetworkPolicy. This verifies rule routing and suppression with synthetic metrics, not an actual wallet lock transition.

Both chain-sync and inactive-channel alerts entered pending and reached Alertmanager after their five-minute duration; the runner exited `0` and removed its Pod, Service, and NetworkPolicy. This confirms that the suppression condition did not disable the ordinary synthetic fault path.
21. Confirmed all three LND Pods still lacked `wallet.db`, then deleted the disposable `lnd-monitoring` namespace. 22. On that freshly recreated monitoring stack, reran `ops/test-lnd-alerts --wallet-locked`. The locked-wallet fixture again reached Alertmanager, while dependent alerts stayed suppressed with its lndmon target up; the runner exited `0` and removed the fixture Pod, Service, and NetworkPolicy. This proves the synthetic wallet alert delivery path after the monitoring namespace reset.
23. Ran the changed arm64 collector container with an isolated fake state response and no read-only macaroon file. Its `/wallet-state` HTTP route returned the one-hot `LOCKED` metric with status 200, while its payment `/metrics` route returned 503 because the macaroon was absent. This checks route separation and fail-closed payment collection inside the image; the earlier live LND `/v1/state` call checked TLS and the actual `NON_EXISTING` response separately. A live locked-wallet sidecar scrape still awaits wallet setup.

The monitoring namespace reset did not delete cluster-scoped monitoring CRDs, K3s image caches, or the K3s cluster. A later [full Mac project VM clean run](mac-full-clean-wallet-state-2026-09-22.md) recreated this wallet-state configuration from VM and namespace absence after removing local project image tags. Both-platform proof, wallet-dependent LND, lndmon, and payment collector scrapes, live LND dashboard samples, receive failure semantics, and real LND fault injection remain outstanding. The monitoring namespace uses privileged Pod Security Admission for node exporter host mounts; the LND namespace stays at its separate baseline setting.
