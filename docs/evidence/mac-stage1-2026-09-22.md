# Mac stage 1 clean-start evidence (2026-09-22)

Host: macOS arm64. Project VM name: `lnd-ops-k3s`. No project Kubernetes namespace or funded wallet existed in the VM before deletion.

1. `ops/bootstrap` created the Lima VM and started K3s `v1.36.4+k3s1`. `kubectl get nodes` reported `lima-lnd-ops-k3s Ready`.
2. Running `ops/bootstrap` a second time reused the running VM and returned the same Ready node.
3. `kubectl get ns` showed only Kubernetes default namespaces; `k3s secrets-encrypt status` reported `Encryption Status: Enabled`.
4. `limactl stop lnd-ops-k3s && limactl delete --force lnd-ops-k3s` removed the entire project VM. `limactl list` then reported no instance.
5. Running `ops/bootstrap` again created a new VM from the cached, checksum-identified Ubuntu image and installed K3s. `kubectl get nodes` again reported `lima-lnd-ops-k3s Ready`, version `v1.36.4+k3s1`.

The Ubuntu download cache remained on the Mac, so this proves recreation from zero project VM and Kubernetes resources, not a fresh download. The Windows WSL 2 exit check remains unverified.

After the initial run, the bootstrap installer was changed to download Lima v2.2.0 from its official release archive when the exact version is absent. The archive checksum `bbdef91774885a0d05f7b048c4eb89ae2bcf3a0c252ae7ca7934e63df76d93c3` was verified, and `LND_OPS_USE_BUNDLED_LIMA=1 ops/bootstrap` used that local bundle successfully against the existing Ready cluster. A fresh VM recreation using the bundled CLI remains to be checked.
