# Testnet 라우팅 노드 상시 운영 계획

상태: 구현 진행 중. 아래 체크 목록과 검증 근거가 모두 충족되기 전에는 완료가 아니다.
범위: 기존 testnet 지갑과 채널을 보존하며 Mac·WSL에서 구축, 검증, 지속 운영을 연결한다.
이 문서의 단계 번호는 구현 순서이며, UI의 Phase 1~11 번호는 유지한다.

## 구현 추적

- [x] JSON 준비 상태 조회 추가. 외부 도달성·실경유는 아직 미검증으로 명시.
- [x] Phase 2 개인 결제·Router 채널 선행 조건 제거; testnet 관측의 개인 결제 강제 조건 제거.
- [x] 기존 CLI 완료 판정과 JSON 조회를 단일 경로로 통합. 과거 경유 이벤트 하나로 완료 처리하는 경로 제거.
- [x] 대화형 상태 전이, 독립 조회 작업자와 1초 UI, timestamp 의미 수정.
- [ ] 승인된 채널 개설, 예산·수수료 제한, 요청 기록과 모호한 결과 재조정.
- [ ] 외부 P2P 검사와 외부 payer 경유 검증 증거, identity/channel 바인딩.
- [ ] 셸과 독립적인 운영 서비스, Mac/WSL 부팅 연결, 제한된 복구.
- [ ] 기존 지표 재사용, 운영 경보·백업 상태·kagent 읽기 전용 진단.
- [ ] Phase 1~11 흐름 및 관련 runbook 동기화.
- [ ] 실제 testnet 통합, Mac/Windows 재부팅·주소 변경·복구 증거.

현재 구현: `router-channel`은 연결된 peer 선택, 예산·입력·수수료 요약과 OPEN 승인,
단일 writer lock, 제출 전 영속 기록, 모호한 결과의 중복 방지를 지원한다.
응답 유실로 funding point를 잃어도 pending 채널의 memo·peer·금액을 대조해 복구한다.
기록된 point의 종료는 동일 peer·금액, 종료 거래와 양수 close height가 있는 경우에만
`closed`로 해소한다. 종료 대기·abandoned·funding canceled는 재요청을 허용하지 않는다.
식별할 수 없는 요청을 운영자 말만으로 실패 처리하는 우회 기능은 제공하지 않는다.
`router-peers`는 지갑 identity에 묶인 공개키·주소 승인과 제한된 재연결을 지원한다.
`router-monitor`는 셸과 별도로 실행할 수 있는 감시 실행기다. 단일 인스턴스 잠금,
조회 프로세스 시간 제한·종료, 승인 peer 복구, 지속 상태 경보와 heartbeat 기록을 지원한다.
`router-service`는 기본적으로 설정만 출력하며, Phase 3의 지속 감시 메뉴에서 명시적 승인 후
Linux systemd / Mac LaunchAgent를 설치한다. Linux/WSL 시작과 Mac 로그인에 연결되지만
Mac은 추가 동의를 받으면 기존 프로젝트 VM을 먼저 시작하고 감시로 넘어간다.
Windows는 추가 승인을 받아 현재 사용자 로그인 시 기존 WSL을 시작하는 작업을 등록한다.
로그인 전 무인 부팅과 실제 호스트 복구 검증은 아직 남아 있다.
미확정 요청의 운영자 재조정과 실제 호스트 재부팅 검증도 미완료다.
채널 개설 응답 뒤와 기존 요청 재확인 때 로컬 암호화 SCB 상태를 읽기 전용으로 표시한다.
백업 조회 실패는 개설 결과를 바꾸거나 재제출을 허용하지 않는다. 대기 채널의 백업 포함은
별도로 확인해야 하므로 활성화 뒤 지원 메뉴에서 재확인·갱신하도록 안내한다.
이 연결을 포함한 Router Python 180개 및 기존 SCB 테스트 2개가 통과했다.
준비 상태가 정상이면 실경유 증거를 요구하고, 이어 외부 접속 결과를 요구한다.
현재 준비 상태·현재 채널에 묶인 실경유 이력·유효한 외부 검사 결과가 모두 있으면
Phase 3을 완료한다. 외부 위치는 운영자가 확인한 사실로 표시하며 독립 검증으로 표시하지 않는다.

SSH 서버 없이 별도 네트워크에서 실행할 수 있는 `observer/` 검사기를 추가했다.
일회용 키로 요청한 공개키의 Brontide 인증과 Lightning init 수신까지 확인한다.
공개 IP의 TCP 9735 한 곳만 대상으로 하고 전체 15초/요청 만료 시각으로 제한한다.
검사자의 외부 네트워크 위치는 자동 증명하지 못하므로 운영자 확인으로 명시한다.
`router-observation` CLI가 현재 testnet 공개키·공개 주소에 묶인 10분 요청을 발급하고
저장한 nonce·시각·응답 키·현재 주소를 대조해 결과를 가져온다. 만료·지갑/주소 변경 시
결과를 무효화하며, 서명 없는 운영자 실행 결과임을 보존한다. Phase 3 메뉴에서
요청 파일 생성·결과 가져오기를 진행하고 만료 시각을 표시한다. 검사기 실행과 파일 전달은
외부 컴퓨터에서 운영자가 수행한다. 검사기만으로 Phase 3을 완료하지 않는다.
실제 외부 testnet 접속은 실행하지 않았다. 사용법과 한계는 [검사기 안내](../observer/README.md)에 있다.
검사기 Go race 테스트는 외부 네트워크 없는 digest 고정 Linux 컨테이너에서 통과했다.
요청·결과 대조 회귀 테스트 8개도 같은 방식의 Python Linux 컨테이너에서 통과했다.

`router-proof`는 제어 가능한 두 외부 SSH peer를 대상으로 단일 결제 검증을 구현한다.
승인은 세 지갑 identity, 현재 입·출력 채널 ID/point, 금액 및 수수료 상한에 묶인다.
동일 작업 잠금 안에서 제출 전 기록을 저장하며, 응답 유실 후에는 기존 결제만 조회한다.
생성 invoice·해석 invoice·수신 invoice의 hash, 송신 성공 경로, 로컬 경유 기록을 대조한다.
이전 성공은 현재 채널 구성의 초기 검증 이력이며 현재 가용성을 대신하지 않는다.
송신·Router·검증 실행 호스트의 시각이 맞아야 한다. 시간 범위를 벗어난 결과를 성공으로 보정하지 않는다.
현재는 직접 연결된 제어 가능한 공개 peer 한 쌍을 지원한다. 임의 공개 peer를 대상으로
원격 결제를 실행할 수 있다고 가정하지 않는다. 실제 testnet 시험과 외부 P2P 검사는 아직 남아 있다.

검증: 전체 Python 216개 테스트가 digest 고정 Python 3.13 Linux 컨테이너에서 통과.
VM 시작의 재시도 간격·중단 기록·잘못된 승인·symlink 거부 회귀 검사를 포함한다.
감시 실행기의 실제 프로세스 중복 차단·SIGTERM 종료 및 상태 기록을 포함한다.
`ops/verify-source`의 Node 95개 및 Helm 검증 통과.
격리된 pinned Bitcoin/LND regtest에서 승인 입력 제한, 수수료 상한,
응답 유실 후 중복 차단·memo 복구, 소비된 입력의 대체 금지, LND 재시작 후 identity·채널 보존을 확인했다.
응답 유실 뒤 블록 생성 전 pending memo로 funding point를 찾는 경로도 실제 LND에서 통과했다.
종료 기록 판정은 현재 모의 RPC 회귀 테스트로 확인했으며 실제 종료 시험과 구분한다.
재현 명령은 `python3 tests/integration_router_funding.py`이며 실제 testnet 지갑에는 접속하지 않는다.
관측 수수료는 166 sat, 승인 상한은 3,000 sat였다. 이 값은 해당 시험 거래의 결과다.
같은 격리 시험에 세 번째 LND를 추가해 독립 payer → Router → receiver의 실제 결제도 검증했다.
성공 결제 응답을 유실시킨 뒤 두 번째 제출을 차단하고, 기존 결제 hash·수신 invoice·경유 기록으로 복구했다.
Phase 3 추가 검증: Router 관련 Python 176개가 digest 고정 Linux 컨테이너에서 통과했다.
채널 그래프의 정책 미수신과 pinned LND의 `GetChanInfo` missing-edge 응답을 대기로
구분하며, 권한·연결·Kubernetes 조회 오류는 숨기지 않는다. 격리된 실제 LND에서도
missing-edge 응답 분류와 위 채널 개설·재시작·실경유 회귀 시험이 통과했다.
이 과정에서 pinned lncli의 `scid`(숫자)와 `chan_id`(32바이트 hex)를 구분하는 회귀 테스트를 추가했다.
이 결과는 전체 구현이나 실제 호스트 복구를 증명하지 않는다.

채널 개설 구현 근거: pinned LND v0.21.3-beta의
[`wallet_assembler.go`](https://github.com/lightningnetwork/lnd/blob/v0.21.3-beta/lnwallet/chanfunding/wallet_assembler.go)
는 지정 outpoint가 소비되거나 잠겼으면 실패하고, 지정 입력 목록 안에서만 coin selection한다.
선택 목록 중 일부만 쓰는 것은 허용하지만 목록 밖 입력으로 대체하지 않는다.
현재 수수료 상한은 표준 segwit 입력만 허용하고 입력당 200 vB, 출력·헤더 등 1000 vB,
dust change 1000 sat를 추가한 보수적 경계다. 위 pinned LND를 실행한 regtest 시험에서
실제 거래 수수료·memo 복구·응답 유실을 검증했으며 모든 입력 유형·크기 조합을 증명하는 시험은 아니다.
요청 복구의 권위 있는 기록은 `open-request.json`이며 `open-<id>.json`은 보조 이력이다.
두 파일 갱신 사이 중단돼도 활성 기록을 먼저 읽고 미확정 요청의 재전송을 차단한다.

실환경 읽기 전용 확인: WSL은 기존 `208cdb3`이며 새 서비스는 미설치다.
체인·그래프 동기화, 공개 활성 채널 1개, private 비활성 2개, pending 0개를 확인했다.
현재 작업트리 verifier를 SSH 조회 어댑터로 실행한 결과는 `channel_required`였다.
Mac의 `lnd-ops-k3s` VM은 정지 상태다. 사용자는 외부 SSH 검사 서버가 없다고 확인했다.
9월 23일 Pod 재시작 복구(205초)와 9월 24일 testnet 송수신·백업·관측·재배포 성공
기록은 보존한다. 당시 `phase3-acceptance`는 관측 검증이며 현재 Router Phase 3과 다르다.
현재 LND의 전체 forwarding 조회는 0건이다. 이 사실로 과거 일반 송수신 성공을 무효화하지 않는다.

Phase 3 서비스 검사 보강: NodePort 유형, 정확한 첫 노드 selector, TCP 프로토콜,
서비스·대상 포트 9735와 NodePort 30973을 함께 검사한다. 다른 포트·노드로 연결되거나
추가 포트가 노출된 서비스를 과거 검증 이력으로 완료 처리하지 않는다. Router Python
182개 및 Helm 관련 테스트 3개가 통과했다. 현재 WSL의 실제 서비스 JSON을 읽기 전용으로
조회해 새 검사에 통과함을 확인했다. EndpointSlice·외부 접속 검증 또는 WSL 코드 배포는 아니다.

## 운영 목표와 한계

대화형 흐름 회귀 검증은 `tests/test_router_interaction.py`에 있다. 모의 verifier
결과로 unlock부터 외부 검사 완료까지 안내 순서, helper 성공만으로 완료하지 않는지,
사용자가 정책 적용을 건너뛴 뒤 명시적 재시도, 조회 오류 중 기존 채널 표시 보존을 검사한다.
외부 접속 결과가 만료됐거나 노드 조회 시각이 미래 또는 30초보다 오래되면 완료를 거부한다.
완료·q 입력·Ctrl+C 경로의 worker 정리도 확인한다. 실제 terminal 입력·RPC·결제
검증과는 별개다. 이 5개를 포함한 Router 테스트 187개가 digest 고정 Linux 컨테이너에서 통과했다.

목표는 결제를 전달할 수 있는 상태를 유지하고, 장애를 감지·복구하는 것이다.
외부 결제가 계속 발생하거나 다른 노드가 항상 온라인인 것은 보장할 수 없다.
호스트 전원·인터넷·디스크와 충분한 유동성도 필요하다. 노트북 절전 또는
Windows 재부팅으로 WSL이 정지하면 그동안 라우팅은 중단된다.

공개 채널 두 개는 이 랩의 최소 시작 조건이다. 서로 다른 peer와 연결하고,
들어오는 채널의 inbound와 나가는 채널의 outbound가 함께 있어야 한다.
두 채널 모두 local balance가 있다는 사실만으로 경유 가능한 경로가 증명되지는 않는다.

기본 운영 정책 제안:
- 읽기 전용 감시, 이미 승인한 peer 재연결, 동일한 포트 전달 복구는 자동 실행한다.
- 채널 개설·닫기, 송금, swap, 리밸런싱은 금액·수수료를 보여주고 승인받는다.
- 초기에는 지갑 unlock을 대화형으로 유지한다. 완전 무인 재시작은 별도의 보안 설계가 필요하다.
- testnet 전용으로 시작하며 mainnet에는 같은 설정을 자동 적용하지 않는다.

## 구현 시작 시 확인한 문제

아래 표는 최초 진단이다. 해결 여부는 위 구현 추적과 실제 검증 결과를 기준으로 한다.

| 위치 | 문제 | 영향 |
|---|---|---|
| `ops/start: guide_router` | 채널이 없을 때도 조회만 반복 | pending 채널이 없으면 기다려도 진행되지 않음 |
| `ops/verify-router` | 서로 다른 peer 및 inbound 조건 미검사 | 채널 수만 맞아도 유동성 부족을 놓침 |
| `ops/verify-router` | URI 유무만 검사 | 실제 외부 P2P 도달성을 증명하지 못함 |
| `ops/configure-router-policy` | max HTLC를 local balance - 1 sat로 설정 | reserve·진행 중 HTLC 등을 반영하지 못함 |
| `ops/verify-router: policy_matches` | max HTLC와 현재 local balance의 정확한 일치 요구 | 정상 결제 후 잔액이 변하면 정책 재적용 요구 |
| `ops/verify-router` | 전체 이력 중 forwarding 하나만 검사 | 현재 구성의 경유 검증 여부를 구분하지 못함 |
| `ops/start: refresh_router_clock` | 조회 자체는 화면 스레드에서 실행 | 느린 RPC 동안 1초 시계도 멈춤 |
| `ops/verify-testnet-readiness`, `ops/verify-monitoring` | 사용자 송수금을 기반으로 완료 판정 | 라우팅 전용 운영에 불필요한 결제 요구 |

## 1. 상태 판정부터 바로잡기 — 첫 MVP

수정: `ops/verify-router`, `ops/start`, `ops/configure-router-policy`.

- 문자열을 해석하는 분기를 구조화된 상태 결과로 교체한다. JSON 출력과 기존 CLI 종료 코드를 함께 지원한다.
- 지갑 잠김, 동기화, peer 단절, 채널 미개설, funding 확인 대기, 유동성 부족,
  정책 미설정, 경유 증거 없음, 조회 오류를 각각 구분한다.
- active뿐 아니라 pending·inactive·private 채널과 서로 다른 peer 수를 표시한다.
- pending=0이고 채널이 부족하면 즉시 개설 안내로 전환한다. 블록 확인이 필요한 경우에만 확인 수를 기다린다.
- last checked, 실제 채널 상태 변경 시각, graph sync 상태를 구분한다.
  현재 채널 수 변경 시각을 '최근 채널 동기화'라고 부르는 표시를 수정한다.
- 수수료 정책은 저장된 목표 정책과 비교한다. 잔액 변화는 정책 위반으로 보지 않는다.
  max HTLC는 채널 제약 안의 정책 상한으로 관리하고 실제 전송 가능 잔액은 별도로 계산한다.
- 조회는 단일 작업자로 직렬 실행하고 UI 시계는 독립적으로 1초 갱신한다.
  중첩 조회를 금지하고 마지막 성공 조회 시각·오류·오래된 결과를 표시한다.

완료 기준: 공개 채널 1개/pending 0개에서 개설 안내가 나오고, pending이 있으면 중복 개설하지 않는다.
결제 후 잔액이 달라져도 정책을 재적용하지 않으며, 느린 조회에도 시계와 중단 입력이 동작한다.

정책 목표는 현재 지갑 identity와 함께 `policy.json`에 저장한다. 저장 및 모든 변경 RPC는
같은 작업 잠금 안에서 실행한다. 일부 RPC 실패 시 앞선 채널은 이미 변경됐을 수 있고,
같은 목표를 다시 승인하면 재적용할 수 있다. `applying`은 중단·부분 적용·마지막 기록 실패를
포함하므로 완료 증거가 아니다. 실제 그래프 정책을 다시 비교한다. 비교 대상은 새로 활성화된
채널까지 포함한 현재 활성 공개 채널이며, 두 peer 조건은 별도로 검사한다.
max HTLC는 `min(capacity_sat × 1000, local_constraints.max_pending_amt_msat)`로 계산한다.
잔액 변화에는 영향받지 않지만 채널 제약이 바뀌면 다시 비교한다. 잘못된 저장 형식과 다른
지갑의 정책은 거부한다. 비공개·비활성 채널에 자동으로 정책을 적용하지 않는다.

## 2. 대화형 공개 채널 개설

수정: `ops/start`, `ops/testnet-peer-candidates`. 추가 제안: 채널 개설 전용 helper.

1. 기존 지갑·채널과 확인된 온체인 잔액, 예약금, 수수료 여유를 먼저 표시한다.
2. 기존 peer와 후보의 공개키, 주소, 관측된 연결 상태를 보여준다. 그래프 정보만으로 신뢰성을 보증하지 않는다.
3. 다른 peer를 선택하고 채널 금액·최대 수수료를 입력받는다.
4. 자금이 채널에 묶인다는 설명과 최종 요약을 보여주고 명시적으로 승인받는다.
5. 상대 수락 후 funding txid와 채널 식별자를 기록하고 확인 수·활성화·공개 전파를 추적한다.
6. 거절·잔액 부족·최소 용량 조건은 한국어로 설명하고 다음 선택을 받는다.

중복 실행 방지: 실행 잠금, 요청 기록, pending 조회와 기존 채널 대조를 사용한다.
RPC 타임아웃은 개설 실패로 단정하지 않는다. 결과를 재확인하기 전에는 재요청하지 않는다.
funding 식별자를 받기 전 타임아웃이라면 pending 목록이 비었다는 이유만으로 재시도하지 않는다.
온체인 거래·peer·요청 기록까지 대조하고, 미해결 요청은 사용자 확인이 필요한 상태로 유지한다.
기존 private 채널은 자동 폐쇄·재개설하지 않는다. 채널 변경 후 백업 갱신 상태도 표시한다.

완료 기준: 재실행과 응답 유실 후에도 같은 요청으로 funding 거래가 중복 생성되지 않는다.

## 3. 유동성과 실제 경유 검증

수정: Router verifier, `ops/testnet-payer`, UI Phase 3·4.

- 채널별 reserve, pending HTLC, peer 정책을 고려해 송신 가능량과 수신 가능량을 보수적으로 표시한다.
  원격 잔액 기반 값은 전체 외부 경로 성공을 보장하는 값으로 표시하지 않는다.
- 초기에는 공개 채널 2개/서로 다른 peer 2개와 작은 시험 결제를 위한 입·출구를 요구한다.
  준비 상태는 사용자에게 제시한 시험 금액과 수수료 상한을 기준으로 판정한다.
  그보다 큰 모든 결제까지 전달 가능하다는 의미로 쓰지 않는다.
- inbound가 부족하면 외부 노드의 채널 개설 또는 승인된 유동성 작업을 안내한다.
  Loop 지원 네트워크·서버·최소 금액·quote는 실행 시 확인한다. Loop 설치만으로 부족 상태를 해소했다고 처리하지 않는다.
- 별도 payer와 receiver가 준비됐을 때만 시험 결제를 실행한다. 사용자가 제어하는 외부
  지갑 또는 협조한 운영자의 환경이 필요하며, 임의 공개 peer에 결제를 요구할 수 있다고 가정하지 않는다.
- 시험 시작 시각, payer 결과, 해당 노드의 입·출력 채널 ID, forwarding event를 대조한다.
  과거 이벤트 하나 또는 내 노드가 수취한 invoice는 이번 경유 성공으로 인정하지 않는다.
  payer의 성공 결과와 로컬 경유 기록을 모두 요구한다. 지갑 identity나 시험 경로의
  채널이 교체되면 과거 증거는 보관하되 현재 구성에는 재검증이 필요하다고 표시한다.

완료 기준: 통제 가능한 testnet 경로로 실제 경유 1회를 확인한다. 외부 시험 환경이 없으면
'라우팅 준비 완료 / 실경유 미검증'으로 표시하고 Phase 3 완료 이력은 만들지 않는다.

## 4. 셸 종료·호스트 재시작 후에도 운영 유지

수정: 배포 chart, `ops/windows-install-router-refresh`, Mac VM 운영 스크립트.

- 셸은 설정과 상태 화면만 담당한다. 감시·재연결은 독립 서비스로 실행한다.
- 호스트 시작 → VM/WSL → Kubernetes → LND → unlock → peer 재연결 → 상태 검증 순서를 확인한다.
- 현재 WSL service는 WSL이 시작된 뒤의 전달 갱신이다. Windows 부팅 시 배포판 자체를
  시작하는 작업과 실패 재시도까지 별도로 구성해야 한다. Mac도 로그인/재부팅 및 VM 기동을 검증한다.
- 공인 IP 변경, DDNS 선택, 공유기 전달 대상인 Windows LAN IP 예약 상태를 확인한다.
  외부 P2P 검사에는 별도 네트워크의 검사자와 시각이 포함된 결과가 필요하다.
- 지갑이 잠겨 있으면 'unlock 필요'를 표시한다. 이를 자동 복구 완료로 기록하지 않는다.
- 무인 unlock은 추후 선택 기능으로 다룬다. 자격증명 저장소·접근 권한·재부팅 시 가용성을
  확정하고 사용자 승인 후 구현한다. 암호를 Git·명령행·로그에 넣지 않는다.
- 단일 지갑의 단일 writer를 유지한다. 같은 지갑을 여러 LND 인스턴스로 동시 실행하지 않는다.

완료 기준: Pod 재시작 및 실제 Mac/Windows 재부팅에서 같은 pubkey·PVC·채널이 유지된다.
대화형 unlock 모드는 사람의 unlock 이후 복구 시간, 무인 모드는 전체 복구 시간을 각각 측정한다.

## 5. 운영 감시와 제한된 복구

수정: UI Phase 5·9, 기존 exporter/alert/runbook 및 kagent 접근 정책.

- 기존 LND/LNDmon 지표를 재사용한다. 추가 수집은 외부 P2P 도달성, 상태 확인 시각,
  승인된 작업 상태 등 기존에 없는 운영 정보로 제한한다.
- 지갑 잠김, sync 지연, peer 단절, 공개 채널 감소, 방향별 유동성 부족,
  디스크·백업 문제를 지속 시간 기준으로 경보한다.
- 성공 경유 수와 수수료는 활동 지표다. 최근 결제가 없다는 이유만으로 노드를 장애로 판정하지 않는다.
- kagent는 우선 읽기 전용 진단과 기존 runbook 연결을 담당한다. 자금 관련 권한은 부여하지 않는다.
- 승인된 peer 재연결·포트 전달 갱신은 backoff와 재시도 한도를 둔다.
  채널 부족을 이유로 무제한 자동 개설하거나 반복 재시작하지 않는다.
- peer 연결은 첫 요청을 즉시 보내고 실패 후 10초, 다음 실패 후 20초를 기다린다.
  세 번째 요청 후 40초 동안에도 연결이 관측되지 않으면 운영자 확인 상태를 유지한다.
  연결 목록 조회 실패는 단절로 간주하지 않고 연결 요청 예산을 소비하지 않는다.
  실제 연결이 관측되면 다음 단절에 사용할 세 번의 예산을 초기화한다.
  지갑 identity가 달라지면 기존 승인을 사용하지 않으며 현재 지갑과 정확한 공개키·주소를 다시 승인해야 한다.
- 감시가 셸 종료 후에도 유지돼야 한다. 알림 전달처는 별도 선택받고 등록 전에는 상태 UI에만 표시한다.

완료 기준: 장애 지속·복구를 구분해 경보하며, 유휴 상태를 실패로 판단하지 않는다.

감시 실행기의 현재 경보 계약:
- `monitor.json`의 heartbeat는 감시 프로세스 생존 시각이다. 노드 상태 조회 시각을 대신하지 않는다.
  `probe_in_progress`, `observation_received_at`, 각 결과의 `checked_at`/`attempted_at`을 함께 읽는다.
- `last_successful`은 마지막 유효한 조회 결과이며 지갑 잠김 같은 비정상 상태도 포함한다.
  `query_error`가 발생하면 현재 오류와 마지막 유효 결과를 별도로 보존한다.
- 동일한 비준비 코드가 120초 지속될 때 한 번 경보한다. 코드가 바뀌거나 조회 오류가
  발생하면 새 코드의 시간을 다시 센다. 기존 경보가 있었다면 즉시 `condition_changed`를 남긴다.
  준비 상태가 확인될 때만 `recovered`를 남긴다. 감시 중단 시간을 장애 지속 시간으로 합산하지 않는다.
- 감시 결과의 `ready`는 실경유 검증의 `complete`와 다르다. 최근 트래픽을 요구하지 않는다.
- 현재 경보는 로컬 상태·로그에만 기록한다. 외부 알림 연결은 별도 구현한다.
- Router 화면 `v` 또는 `router-monitor --status`는 감시를 시작하지 않고 기록을 조회한다.
  생존 시각 15초, 노드 조회 시각 30초를 넘기거나 미래/잘못된 시각이면 현재 준비됨으로
  표시하지 않는다. 외부 접속 결과는 별도 만료 판정하며 만료만으로 운영 장애를 만들지 않는다.
- 새 노드 관측이 없으면 `observation_stale`, 그 상태가 120초 지속되면 한 번
  `observation_alert`를 기록한다. 관측이 재개되면 `observation_resumed`이며, 지갑 잠김
  같은 노드 장애가 해결됐다는 의미의 `recovered`와 구분한다. 감시 프로세스가 죽은 동안에는
  자체 경보를 쓸 수 없으므로 읽는 쪽에서 heartbeat를 확인해야 한다.

보류된 로컬 초안(이번 Phase 3 커밋에서 제외): kagent의 `diagnose_testnet_router`는 고정된 testnet 첫 노드의 기존 wallet/LNDmon/SCB
지표를 읽는다. 임의 쿼리·namespace·동작 입력을 받지 않고 Kubernetes mutation을 하지 않는다.
지표와 scrape 상태가 두 분 이내의 표본이고 scrape가 성공한 경우만 사용하며,
없거나 오래되거나 잘못된 값은 `unknown`이다. 개인 결제·경유 트래픽을 요구하지 않는다.
공개 채널 구분·HTLC 제약·외부 도달성·실경유는 이 집계 지표로 증명하지 않는다.
진단 도구는 항상 자동 조치 부적격·라우팅 미검증을 반환한다. 관련 runbook을 gateway
패키지와 허용 목록에 연결했다. 고정 Prometheus 이미지에서 실제 쿼리 49개 사례를
실행해 정상·0값·수집기 중단·오래된 표본·다른 namespace/노드 제외를 확인했고 Linux CI에 추가했다.
이 검증은 실제 kagent 배포·모델의 도구 호출·운영 장애 실습을 대신하지 않는다.

서비스 설치는 실패 시 이전 파일과 등록 상태를 자동 복원하지 않는다. 실패 후 현재 등록·실행 상태를
조회해 표시하고 오류 해결 뒤 지속 감시 메뉴에서 재설치하도록 안내한다. 설치 성공은 라우팅 검증이 아니다.
렌더링과 설치 실패 경로는 Linux에서 시험하며, 생성 systemd unit은 `systemd-analyze verify`로 검사한다.
Mac LaunchAgent는 로그인 세션에 등록되므로 로그인 전 무인 부팅 완료를 의미하지 않는다.
`m` 메뉴에서 VM 시작 포함을 선택한 경우에만 `router-vm-start`를 등록한다.
승인 시 기존 VM 이름·디렉터리 inode/device·설정 hash를 저장하고 시작 전에 다시 비교한다.
다른 VM 생성·설정 변경·지갑 복사를 수행하지 않는다. 서비스 실행 중 수동 VM 삭제·재생성은
지원하지 않으므로 먼저 서비스를 중지해야 한다. 승인 기록과 잠금은 현재 사용자 소유의
비공개 일반 파일이어야 하며 symlink/hardlink와 잘못된 기록은 거부한다.
시작 요청은 제출 전에 기록하며 최대 세 번이다. 명령 종료 뒤 30/60/120초 간격을 두고,
시작 중인 VM에는 요청하지 않는다. 시간 초과나 중단은 실패 확정 대신 `uncertain`으로 남긴다.
실제 Running 관측 후에만 감시로 넘기고 다음 시작을 위한 예산을 초기화한다.
감시로 넘긴 뒤 VM 충돌을 이유로 자동 재시작하지는 않는다. 다음 서비스 시작 시에는 다시
기존 VM 상태를 확인한다. 세 번 소진하면 서비스 재시작으로 우회하지 않고 재승인을 기다린다.
Mac plist 구문 검사는 통과했으나 실제 VM 시작·로그아웃/로그인·재부팅 복구는 아직 미검증이다.
이 구분은 [Apple 서비스 문서](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html)와
[systemd 서비스 정의](https://github.com/systemd/systemd/blob/main/man/systemd.service.xml)를 기준으로 한다.

Windows 로그인 시작은 `m` 메뉴에서 감시 서비스 설치 후 별도로 선택한다.
`INSTALL WSL STARTUP` 승인 및 Windows 관리자 권한이 필요하며 암호를 저장하지 않는다.
현재 Windows 사용자의 기존 WSL 2 배포판과 Linux 일반 사용자를 지정하고,
등록된 배포판 GUID·이름·저장 경로가 바뀌면 시작하지 않는다. 배포판을 만들거나 가져오지 않는다.
K3s·Router 감시·포트 전달 갱신 서비스가 enable된 상태에서만 등록한다.
로그인 작업은 WSL 안의 foreground `sleep infinity`를 유지한다. systemd만으로 WSL의
생존이 보장되지 않는다는 [Microsoft 문서](https://learn.microsoft.com/en-us/windows/wsl/systemd)에 따른다.
작업이 예상치 않게 종료되면 1분 간격으로 최대 세 번 재시도한다. 같은 작업의 중복 실행은
막으며, 같은 사용자 소유의 lnd-ops 작업만 교체한다. 다음 로그인 또는 명시적 수동 시작은
새 실행이다. 배터리 사용 중에도 실행하도록 설정하므로 절전·전원 정책은 별도 관리해야 한다.
WSL 포트 전달 갱신은 5분 안에 세 번 실패하면 멈추며 상태 확인 후 운영자가 재시작해야 한다.
`ops/windows-router-startup --mode status`는 작업 등록·실행 상태만 조회한다. Running은
지갑 unlock·포트 도달성·라우팅 성공을 증명하지 않는다. 설치 실패 시 자동 복원하지 않는다.
기본 실행은 미리보기이며 실제 Windows 등록·로그인·재부팅은 아직 시험하지 않았다.
실제 WSL 호스트의 Windows PowerShell에서 현재 `Ubuntu-24.04` 배포판을 찾아
미리보기를 출력하는 읽기 전용 경로는 통과했다. 작업 등록과 배포판 시작은 수행하지 않았다.
같은 호스트의 실제 ScheduledTasks cmdlet에서 1분 간격·세 번 재시도, 실행 시간 제한 없음,
중복 무시, 현재 사용자 로그인·Interactive/Highest 설정 객체 생성도 확인했다.
이는 객체 생성 검증이며 등록·실행·재시도 성공 증거는 아니다.
PowerShell 테스트는 digest 고정 Linux 이미지에서 작업 설정, 승인 거부, 소유권 충돌,
생성 실행문의 실제 실행과 배포판 변경 거부를 검사했다. 레지스트리와 WSL 실행은 모의
대상이며 실제 Task Scheduler의 재시도·종료 동작을 증명하지 않는다. Linux CI에도 이 검사를 추가했다.

## 6. Phase 1~11을 라우팅 운영 모드에 맞추기

| UI Phase | 변경 계획 |
|---|---|
| 1 regtest | testnet 운영과 분리된 선택 실습으로 유지 |
| 2 testnet | 영속 지갑·동기화·연결 상태 확인. 사용자 송수금 이력은 운영 필수 조건에서 분리 |
| 3 Router | 위 1~4단계 적용. 준비 상태와 실경유 검증 이력을 별도 저장 |
| 4 Loop | 필요한 경우 선택. 설치·quote 검증과 실제 swap 승인을 분리 |
| 5 관측 | 수집 성공과 경보 검증으로 완료 판정. 최근 1시간 사용자 결제 강제 조건 제거 |
| 6 보안 | 공개 P2P만 노출, 운영 감시·자격증명의 최소 권한 검증 |
| 7 백업 | 채널 변경 후 SCB 암호화·외부 사본 검증. 복구 실습은 운영 지갑과 격리 |
| 8 장애 실습 | 운영 노드 fault injection은 자동 실행하지 않음. 격리 실습을 기본으로 제시 |
| 9 kagent | 읽기 전용 운영 진단부터 연결 |
| 10 Mac·WSL | 호스트 재부팅·주소 변경·셸 종료 복구를 양쪽에서 실제 검증 |
| 11 데모 | 구축 완료, 현재 준비 상태, 실경유 증거, 복구 증거를 따로 출력 |

초기 Phase 3 진행은 실경유 검증까지 유지하되, 관측과 백업 같은 운영 준비는
Phase 3 대기 중에도 접근 가능하게 한다. Phase 3 완료 없이 Phase 5를 준비해도
Router를 검증 완료로 올리지 않는다. 이후 경유 트래픽이 없는 것만으로 초기 완료 이력을 지우지 않는다.

구현됨: Router 화면의 `o` 지원 메뉴에서 관측 배포·지표 연결·암호화 SCB 생성 및 상태
확인을 실행하고 Router 화면으로 돌아온다. 상태 확인은 hash/기록 비교와 상태 ConfigMap
갱신이며 재복호화나 복구 성공 증거가 아니다. 기존 LND 노드 수를 유지하고 모든 기존
노드가 준비됐는지 확인한 뒤 monitoring을 활성화한다. Loop는 이후 Phase 구축에서
건너뛰는 선택 기능이며 4번을 직접 선택하면 구성한다. UI에는 준비 상태, 날짜가 있는
실경유 이력, 외부 접속 확인을 따로 표시한다. Phase 6~11 전체 운영 통합은 아직 남아 있다.

Router 지원 메뉴 7·8은 외부 암호화 SCB 사본 등록·재검증이다. 기존 암호화 백업 검사에
읽기 전용 모드를 추가해 현재 SCB hash와 로컬 암호화 파일의 일치를 확인하고,
사용자가 지정한 외부 파일의 hash를 대조한다. 지갑 또는 SCB 변경, 외부 사본 변경·누락은
미검증으로 표시한다. 전송·복호화·복구는 하지 않으며 저장 위치는 운영자 확인으로 남긴다.
실제 외부 장치의 보관·복구 시험을 완료했다는 뜻은 아니다. [외부 사본 절차](router-backup-copy.md).
Phase 7 acceptance도 외부 사본의 현재 일치를 필수로 확인한다. 사본이 없거나 오래되면
완료 기록을 쓰지 않으며 UI는 암호화 백업 다음에 외부 사본 확인을 진행한다.
Phase 10은 기존 두 호스트 구축 기록만으로 완료하지 않는다. 두 플랫폼의 기록 참조와
runtime 판정을 확인한 뒤 Router 운영 보고서의 현재 상태·재부팅·주소 변경 조건을 요구한다.
기존 구축 기록은 통과했으나 Router 조건이 남으면 재구축 대신 복구 메뉴를 열고,
사용자가 돌아가기를 선택하면 미완료 상태로 유지한다.

Phase 11 진입과 데모의 Lightning 단계에서 읽기 전용 `ops/router-report`를 표시한다.
구축 리소스 존재, Pod/PVC 상태, 현재 Router 준비, 날짜가 있는 실경유 이력과 외부
접속 검증을 구분한다. Pod 복구 기록은 같은 지갑·현재 공개 활성 채널/peer 구성과
대조하며, 서로 다른 Pod UID와 일관된 준비·검증 시각이 있는 기록만 이력으로 인정한다.
현재 상태를 조회하지 못하면 과거 기록을 현재 구성의 복구 성공으로 표시하지 않는다.
Mac/Windows 재부팅은 `o → 6`의 기준 저장·검증 메뉴로 수집하고 저장된 전후 기록을
다시 검증해 표시한다. 주소 변경은 같은 메뉴의 4~7번에서 기준 저장·검증·취소와
외부 검사 요청/결과 가져오기를 제공한다. 공인 주소 또는 guest InternalIP의 실제 변경,
동일 호스트·지갑·스토리지·채널과 기준 저장 이후의 새 외부 접속 결과를 요구한다.
공인 주소 변경만으로 WSL 내부 전달 갱신을 검증했다고 보지 않는다.
기존 Phase 8 기록으로 이를 대신하지 않는다. 보고서는 어떤 완료 증거도 생성하지 않는다.
Phase 11 완료 검사는 전체 데모 7단계의 순서·개수와 시각을 확인하고, 별도로 Router
운영 증거 완료를 요구한다. 일부 단계만 통과한 데모 기록은 전체 완료로 인정하지 않는다.
`router-report --require-complete`는 현재 리소스와 Router 완료, 유효한 외부 접속,
Pod 복구 및 Mac·Windows 양쪽의 재부팅·주소 변경 이력이 모두 있어야 통과한다.
실제 호스트 재부팅·주소 변경 실험은 미실행이며 현재 완료 증거가 있다는 뜻은 아니다.

호스트 재부팅 수집은 같은 물리 호스트 fingerprint, cluster/node UID, 지갑, PVC/PV,
채널을 보존하면서 호스트와 Kubernetes guest의 부팅 식별자가 모두 바뀌어야 통과한다.
loopback API를 사용하는 로컬 클러스터만 지원하며 원격 클러스터 SSH 터널은 이 시험
계약에 포함하지 않는다. 재부팅과 unlock은 운영자가 직접 수행하며 암호를 기록하지 않는다.
기준 저장·검증 실패·취소는 성공 기록과 분리한다. 시간은 기준 저장부터 최종 관측까지로,
실제 장애 시간이나 무인 복구 시간을 의미하지 않는다. 자세한 절차는
[호스트 복구 runbook](router-host-recovery.md)에 있다. Mac/Windows 실제 식별자 조회는
읽기 전용으로 확인했으며 호스트를 재부팅하지 않았다.

## 구현 순서와 검증

첫 배포 범위는 1~2단계: 잘못된 무한 대기를 없애고 사용자가 실제 공개 채널 개설을 완료하게 한다.
그다음 3단계의 실경유, 4단계 복구, 5~6단계 운영 통합 순서로 진행한다.

각 변경은 Linux에서 상태 전이·RPC 오류·중복 방지·예산 제한 테스트를 실행한다.
새 서비스/이미지는 유지보수되는 Linux 이미지에서 시험하고 가능한 경우 digest를 고정한다.
Mac·WSL에서는 터미널 표시 및 실제 호스트 복구를 따로 검증한다.
regtest로 재현 가능한 자동 시험과 실제 testnet 통합 시험 결과를 구분한다.
24시간 관찰을 최초 운영 검증 구간으로 제안하되, 이는 무중단 보장이 아니다.

현 문서 작성은 채널 개설, 결제, 자격증명 저장 또는 배포의 실행 승인이 아니다.
구현 전 결정할 항목은 채널별/전체 예산·최대 수수료, 외부 시험 경로,
무인 unlock 채택 여부, 절전 정책, 알림 전달처다. 미지정 금전 작업은 승인 대기 상태로 둔다.
